# 项目接入与源码提炼

## 接入前调查

编码前依次检查：

1. 仓库规范、策划文档、开发方案和配置表规则。
2. 配置源目录、生成脚本、生成代码和运行时访问接口。
3. 玩家 Root 数据、序列化器、数据库门面、保存时机和迁移版本。
4. Module 基类、注册顺序和生命周期调度器。
5. 货币、物品、奖励、消耗、条件、属性、角色和装备的已有实现。
6. 事件系统、日志、错误码、UI 查询与刷新方式。
7. 上阵数据和战斗属性快照链路。

把每个需求映射到现有所有者。只有确认没有相同职责后才新增模块或抽象。

## 源码提炼规则

Skill 不携带自行设计的 C# 模板。需要新增模块时，从目标项目最接近的真实实现提炼，并记录：

- 来源文件和选择原因。
- 保留的生命周期、注册、保存和事件约定。
- 删除的具体业务规则。
- 替换的配置类型、数据模型和依赖。
- 新模块仍需确认的问题。

允许做命名参数化、业务剥离和必要依赖适配，不得顺手改写框架生命周期、数据库语义或事件规范。

## 重大改动方案

以下情况编码前必须使用 `assets/系统养成框架方案模板.md`：

- 新增角色、装备或完整经济子系统。
- 修改玩家存档结构或数据权威来源。
- 修改多模块经济事务和奖励链路。
- 修改共享属性合成或战斗快照结构。
- 需要迁移旧档或替换现有 Module 所有权。

方案优先写入项目已有开发方案目录；当前仓库约定可使用 `ai-doc/develop-setup/`，其他项目没有约定时使用 `docs/progression/`。窄范围空判断、事件刷新或显示修复不强制生成。

## 配置与战斗联动

- 配置结构和数据修改由 `$develop-unity-config-tables` 负责，养成 Skill 明确运行时读取、事务和存档影响。
- 上阵数据、属性快照或战斗读取方式变化时同时使用 `$develop-unity-ecs-battle`。
- 养成负责快照生成，战斗负责快照消费；不要让战斗查询或修改局外存档。

## 修改范围

保留用户现有改动，不重排无关模块、不手改生成文件、不批量清理无关乱码。需要 Unity Prefab、面板 AutoGen 或序列化字段配合时，在交付中明确列出编辑器工作。

# Unity 系统养成开发

围绕目标项目真实架构设计和维护局外养成系统。默认优先适配本地存档，但必须先识别项目的数据权威来源、模块生命周期、配置生成、事件和 UI 规则；禁止在已有项目旁边并行搭建第二套养成框架。

## 强制工作流程

1. 判断任务属于需求整理、框架方案、新系统、功能扩展、数据迁移、故障修复还是重构。
2. 修改前阅读目标仓库的 `AGENTS.md`、`ai-doc`、`docs`、策划文档、本地配置规范和存档文档。
3. 定位真实配置源、持久化数据模型、业务 Module、生命周期调度、事件、UI、战斗上阵数据和验证命令。
4. 新增养成系统，或需求会改变存档、经济事务、属性合成、跨模块数据流时，写代码前必须生成系统养成框架 Markdown：
   - 使用 `assets/系统养成框架方案模板.md`。
   - 优先写入项目已有开发方案目录；当前项目默认使用 `ai-doc/develop-setup/`，没有约定时使用 `docs/progression/`。
   - 写清配置、存档、模块、事务、事件、UI、战斗快照、迁移、异常处理和测试。
   - 仍会改变实现的问题必须列入“待确认项”；方案达到可直接开发并经用户确认后再实现。
   - 窄范围修复、纯展示刷新或不改变数据链的改动无需强制生成方案文档。
5. 从零新建完整养成模块时，必须读取并按顺序执行 `references/新模块从0到1开发流程.md`；依次完成方案、配置、存档、公开接口、Module、注册、事务、事件、UI、迁移和验证，并遵守每个阶段下的代码规范与命名规则，不能跳过中间检查点直接写业务代码。窄范围修复不展开该完整流程。
6. 新建或调整基础架构前读取 `references/架构与生命周期.md`。
7. 涉及玩家数据、自动保存、旧档或本地数据安全时读取 `references/数据与本地存档.md`。
8. 涉及货币、物品、奖励、消耗或条件时读取 `references/经济事务与通用模块.md`。
9. 涉及角色、装备、属性、升级、上阵或战斗快照时读取 `references/角色装备属性流程.md`。
10. 根据具体功能读取 `references/系统功能流程.md`。
11. 接入已有项目或需要新增代码骨架时读取 `references/项目接入与源码提炼.md`，从目标项目真实源码提炼，不使用自行设计的 C# 模板。
12. 实现最小且完整的改动；交付前读取并执行 `references/验证规范.md`。

## 不可破坏的分层规则

- 静态配置描述规则和默认值，不保存玩家当前状态。
- 持久化数据只保存恢复业务状态所需的最小真值，不保存可由配置和真值重新推导的缓存。
- 业务 Module 统一负责校验、事务、数据修改和业务事件，UI 不直接写存档。
- 跨模块编排只能通过明确接口、命令或事件完成；避免 UI、引导或战斗直接修改其他模块内部数据。
- 事件在数据成功提交后发送，事件参数顺序和类型必须有中文注释；监听在登出或释放时成对清理。
- 红点、可升级状态和展示属性默认由当前配置与玩家真值推导，不单独持久化。

## 本地存档默认规则

- 优先复用目标项目现有 Root 模型、数据库门面、标脏、批量提交、加密和回滚机制。
- 新用户初始化必须幂等；不能仅依赖可能成为合法值的业务字段判断“是否新号”。
- 集合和字典在定义或加载后保证非空，持久化模型使用强类型字段。
- 所有写入通过项目统一入口，禁止业务代码直接读写磁盘文件。
- 新增或修改字段时明确默认值、旧档迁移、失败回退和兼容验证。
- 如果目标项目由服务端维护权威数据，服从服务端链路，本地数据只按现有设计作为缓存，不能创建第二份本地真值。

## 经济事务规则

- 货币、物品、奖励、消耗和条件共享统一 ID、数量类型、错误码和来源原因。
- 多项操作按“解析 -> 完整校验 -> 构造变更 -> 原子提交 -> 保存 -> 发送事件”的顺序执行。
- 多货币、多物品消耗不能边校验边扣除；任一项不足时不得产生部分修改。
- 奖励计算和奖励发放分离；随机结果先确定，再统一发放。
- 领奖、购买和一次性解锁必须有幂等键或明确完成状态，防止重复点击、重入回调和重启后重复发放。

## 角色、装备与战斗边界

- 角色和装备模块负责解锁、升级、最大等级、槽位、上阵选择、属性合成和战斗快照生成。
- 系统养成与战斗共享的稳定属性定义在 `cfg/attribute/`；只在战斗使用的参数留在 `cfg/battle/`。
- 养成根据基础配置、等级、品质和永久加成生成最终基础属性快照。
- 战斗只消费快照并维护局内临时变化；战斗结束不能把临时增益回写为养成基础属性。
- 快照使用值拷贝或只读结构，不能把养成字典引用直接交给战斗修改。

## Skill 联动

- 需求涉及 XML、xlsx、枚举、bean、属性、奖励、消耗、条件或升级数据时，必须同时使用 `$develop-unity-config-tables`。
- 需求涉及上阵数据、属性快照结构、战斗读取方式或局内属性行为时，必须同时使用 `$develop-unity-ecs-battle`。
- 需求涉及养成 Panel、Item、Prefab 字段契约、AutoGen、按钮交互、界面状态、红点或事件刷新时，必须同时使用 `$develop-unity-progression-ui`。本 Skill 负责业务真值、命令和事件，UI Skill 负责显示和交互；两者都不能越过 Module 直接修改存档。
- `function` 和 `guide` 只作为外围协作系统：它们可以调用养成公开接口，但功能跳转、引导步骤和引导进度仍由各自系统负责。
- 商店、任务、签到、邮件、活动和通行证不是首版核心；实现时复用本 Skill 的配置、存档、经济事务和事件规则，并按目标项目建立独立业务模块。

## 中文注释规则

- 编写代码时，关键字段、关键方法和关键业务逻辑必须补充详细中文注释，保证后续开发者能从注释理解数据来源和设计意图。
- 关键持久化字段、公开命令、事务步骤、等级含义、配置单位、事件参数、存档迁移和异常兜底必须写 UTF-8 中文注释。
- 注释解释数据来源、规则原因、先后顺序、副作用和兼容要求，不能机械重复代码字面含义。
- 遵循目标项目日志风格；发现乱码时只修复受影响区域，禁止借机重写无关文件。

## 交付说明

说明实现行为、配置源、存档模型、模块接口、事件、UI 协作、战斗快照、迁移、执行过的生成与编译命令、验证结果，以及仍需策划或 Unity 编辑器确认的内容。没有执行配置生成、编译或运行验证时必须明确说明原因。

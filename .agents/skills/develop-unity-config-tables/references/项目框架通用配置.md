# 项目框架通用配置

本文件按 `cfg/` 文件夹说明可跨玩法复用的项目配置。每个目录都列出推荐文件名、负责的通用配置、依赖方向和扩展边界。

这些路径是新项目的默认推荐结构。接入已有项目时，必须先检查其真实目录和生成器规则；已有路径不同但职责清晰时保持原结构，不为统一命名强制迁移。

## `cfg/` 根目录

### `cfg/cfg_sc.xml`

配置生成总入口，负责 include 各模块 XML。

- include 顺序优先遵循公共层到玩法层的单向依赖。
- 只登记模块入口，不在这里定义具体玩法字段。
- 新增或迁移模块后，检查路径、大小写和重复 include。

推荐依赖顺序：

```text
common.xml
  -> global、asset、sound、localize、error
  -> common、attribute、item、bonus
  -> user、function、guide
  -> role、equip、skill、battle、level 等玩法模块
```

生成器允许前向引用，也不能依赖它制造公共模块到玩法模块的反向依赖。

### `cfg/common.xml`

保存所有模块都可使用、且不依赖任何业务的基础值 bean。

| 通用配置 | 推荐结构 | 最小字段 | 使用范围 |
| --- | --- | --- | --- |
| `Vector2` | bean | `x/y:float` | 二维位置、尺寸、偏移 |
| `Vector3` | bean | `x/y/z:float` | 三维位置、角度参数、缩放 |
| `Vector2Int` | bean | `x/y:int` | 网格坐标、整数区间 |

基础值 bean 只表达数据，不包含坐标系、碰撞、移动、伤害或地图规则。单位和业务含义由实际使用字段的中文注释说明。

需要整数、长整数、浮点或字符串联合值时，优先评估它是否真的跨模块复用。普通固定字段应直接使用明确类型，不能为了“通用”全部包装成多态数值。

## `cfg/global/`

### 文件职责

| 文件 | 内容 |
| --- | --- |
| `cfg/global/global.xml` | 定义全局参数类型和 `Global` config |
| `cfg/global/global.xlsx` | 配置全项目按 key 查询的公共参数 |

### 通用配置

`Global` 适合少量真正跨模块、按 key 查询且类型可能不同的数据，例如框架开关、公共服务参数和全项目默认值。

- 使用稳定 `key` 作为主键。
- 使用多态值 bean 区分整数、长整数、浮点、布尔和字符串，避免运行时解析字符串。
- 策划说明字段可以只生成到设计端。
- 运行时通过统一配置服务按类型读取，并允许调用方提供安全默认值。

角色、装备、战斗或 AI 等模块拥有一组结构稳定的参数时，应在自己的目录建立独立 `mode="one"` 配置。同一个参数不能同时存在于 `global.xlsx` 和模块单行表。

## `cfg/asset/`

### 文件职责

| 文件 | 内容 |
| --- | --- |
| `cfg/asset/asset.xml` | 定义资源信息父 bean、资源子类型和 `Asset` config |
| `cfg/asset/asset.xlsx` | 配置稳定资源 ID 到加载信息的映射 |

### 通用配置

`Asset` config 最少包含稳定资源 ID 和资源信息 bean。资源信息按项目资源系统能力扩展，例如纹理、精灵、Prefab 或骨骼动画。

- 路径、图集名、子资源名、默认动画和加载参数只放在资源信息中。
- 业务表只引用资源 ID，不保存真实路径。
- 运行时通过统一资源服务读取配置并加载。
- 项目没有使用的资源类型不要提前创建。

该目录只描述资源定位和加载信息，不能保存角色伤害、装备属性、关卡规则等玩法数据。

## `cfg/sound/`

### 文件职责

| 文件 | 内容 |
| --- | --- |
| `cfg/sound/sound.xml` | 定义音频信息、音频类别和 `Sound` config |
| `cfg/sound/sound.xlsx` | 配置音频 ID、资源路径或资源 ID |

### 通用配置

`Sound` 使用稳定音频 ID 连接业务事件与音频资源。音频信息可区分音效、音乐等基础类别。

- 音量分组、循环、淡入淡出、并发限制等字段只有在音频系统支持时才加入。
- 运行时统一通过音频服务播放。
- 战斗、用户界面和业务代码不能硬编码文件路径。
- “什么时候播放”属于业务规则，不写进公共音频表。

## `cfg/localize/`

### 文件职责

| 文件 | 内容 |
| --- | --- |
| `cfg/localize/localize_sc.xml` | 定义语言枚举、文本本地化和可选图片本地化结构 |
| `cfg/localize/language.xlsx` | 配置文本 key 与各语言内容 |
| `cfg/localize/textureLanguage.xlsx` | 可选，配置不同语言的图片及布局元素 |

### 通用配置

文本本地化使用稳定 key 映射多语言内容；业务表保存本地化 key，不重复写多语言文本。

- 语言枚举值需要与运行时语言系统建立明确映射。
- `language.xlsx` 只配置项目实际支持的语言。
- 图片本地化只在不同语言确实需要独立图片或布局时启用。
- 图片元素可以组合资源 ID、位置、缩放和尺寸等通用数据。
- 新增语言时同步检查字体、文本、图片和运行时语言选择。

语言缺失时的回退顺序由本地化系统统一决定，不能由每个业务模块分别实现。

## `cfg/error/`

### 文件职责

| 文件 | 内容 |
| --- | --- |
| `cfg/error/error.xml` | 定义 `Error` config |
| `cfg/error/error.xlsx` | 配置错误 key 或错误码对应的展示信息 |

### 通用配置

错误配置最少包含稳定错误 key 和描述或本地化 key。

- 面向玩家的错误内容优先引用本地化 key。
- 仅开发可见的诊断信息交给日志系统。
- 网络、配置和业务失败通过统一错误处理入口转换。
- 错误表只描述展示信息，不决定重试、补偿、断线或封禁规则。

## `cfg/common/`

该目录保存多个业务系统共享的经济基础结构和通用条件结构。它与根目录 `cfg/common.xml` 不同：根文件只放基础值对象，本目录可以依赖资源、物品等公共业务配置。

### `cfg/common/common.xml`

推荐定义以下通用内容：

| 通用配置 | 推荐结构 | 职责 |
| --- | --- | --- |
| `ECurrencyType` | enum | 区分跨系统使用的货币类型 |
| `Currency` | config | 配置货币名称、本地化描述、图标和可选品质 |
| `Cost` | 多态 bean | 描述一次操作需要付出的资源 |
| 通用数值联合体 | 多态 bean，可选 | 保存确实需要动态数值类型的公共数据 |

对应数据文件：

| 文件 | 内容 |
| --- | --- |
| `cfg/common/currency.xlsx` | 货币类型、名称、描述、图标和展示信息 |

`Cost` 通常作为其他表的 bean 展开，不单独建立 xlsx。通用子类型只保留稳定能力：无消耗、货币消耗、物品消耗、逻辑与组合、逻辑或组合。

广告、真实货币或活动票券只有在多个模块共享，并且运行时已有统一支付适配器时才进入公共层。消耗配置只描述需求，余额检查、扣除事务、失败回滚和支付确认由运行时服务负责。

### `cfg/common/condition.xml`

定义通用 `Condition` 多态父 bean，通常不需要独立 xlsx，由角色、商店、任务等业务表直接展开使用。

通用子类型可以包含：

- 无条件。
- 货币数量条件。
- 物品数量条件。
- 逻辑与组合。
- 逻辑或组合。

角色等级、竞技场开放、任务状态等具体条件不能写死在公共条件模块。如果生成器不支持跨模块扩展父 bean，业务模块应定义独立条件 bean，再由统一条件服务通过适配器调用。

条件判断必须保持只读，不能在检查过程中扣资源、发奖励或触发战斗。

## `cfg/attribute/`

属性配置属于业务通用层，但只承载需要在系统养成与战斗之间共享的稳定属性契约。系统养成、角色、装备、技能和战斗可以共享同一套属性类型、数值格式和展示元数据，但各模块仍分别负责自己的基础值、成长值和运行时变化。

### 文件职责

| 文件 | 内容 |
| --- | --- |
| `cfg/attribute/attribute.xml` | 定义属性枚举、属性数值类型、属性数据 bean 和 `Attribute` config |
| `cfg/attribute/attribute.xlsx` | 配置属性名称、描述、数值格式和策划说明 |

### 属性归属判断

判断一个数值是否应进入 `cfg/attribute/`，不能只看战斗代码是否读取它，而要看它是否需要由系统养成持久化、计算或展示，并作为稳定属性传入战斗。

| 使用范围 | 推荐路径和文件 | 定义规则 |
| --- | --- | --- |
| 系统养成与战斗共同使用 | `cfg/attribute/attribute.xml`、`cfg/attribute/attribute.xlsx` | 在 `EAttributeType` 中分配稳定属性 ID，并在 `Attribute` 中配置名称、描述和数值格式。养成系统计算最终基础值，战斗通过属性快照读取。 |
| 只在系统养成使用 | 对应养成目录，例如 `cfg/role/role.xml`、`cfg/role/roleUpgrade.xlsx`、`cfg/equip/equip.xml`、`cfg/equip/equipUpgrade.xlsx` | 保留在拥有该数据的养成模块中。没有跨系统稳定语义时，不为它注册公共属性。 |
| 只在战斗使用 | `cfg/battle/` 下对应的战斗专属配置，例如 `cfg/battle/battleGlobal.xml`、`cfg/battle/battleGlobal.xlsx` | 使用明确字段、战斗专属 enum、bean 或 config 定义。局内计时、动作窗口、战斗判定和表现参数不能仅因参与公式就进入公共属性枚举。 |

`cfg/attribute/` 是系统养成与战斗之间的属性契约边界：

- 生命上限、攻击、移动速度等若会被等级、装备、升级或永久养成改变，并影响战斗，应定义为公共属性。
- 格挡恢复时间、攻击阶段窗口、战斗状态计时、相机或动画表现参数只服务局内规则时，应定义在 `cfg/battle/` 的专属配置中。
- 战斗专属数值优先使用含义明确的字段；只有确实需要属性列表、统一格式或运行时加减能力时，才在 `cfg/battle/` 定义战斗专属属性结构。
- 一个数值只在养成界面计算或展示、不会形成战斗输入时，保留在对应养成模块，不进入公共属性表。

### 通用配置

属性目录推荐包含以下结构：

| 通用配置 | 推荐结构 | 职责 |
| --- | --- | --- |
| `EAttributeType` | enum | 为养成、装备、技能和战斗提供稳定属性标识 |
| `EAttrNumberType` | enum | 定义固定值、比例、时间、小数或每秒值等存储与显示规则 |
| `AttributeInfo` | 多态 bean | 作为其他配置表填写属性数据的统一结构 |
| `AttributeNumber` | bean | 属性类型加通用数值联合体，适合确实需要多种数值类型的场景 |
| `AttributeLongNumber` | bean | 属性类型加长整数存储值，适合统一定点数规则的属性列表 |
| `Attribute` | config | 保存属性名称、描述、数值格式和设计说明 |

属性枚举值会被存档、养成数据、战斗快照和网络数据长期引用，必须保持稳定：

- 新增属性使用未占用值。
- 删除属性后不复用旧值。
- 重命名属性时同步检查存档、配置、生成代码和运行时映射。
- 基础、增加、减少等关联属性不能只依赖枚举值相邻关系推断，应由明确的运行时代码或配置关系管理。

### 数值格式

属性原始值和展示值必须分层：

- 配置和存档保存统一原始值。
- `EAttrNumberType` 决定原始值如何转换为整数、比例、秒数、小数或每秒值。
- 比例缩放、时间单位和小数精度在项目内只能有一套规则，并在属性格式化服务中统一实现。
- 用户界面通过属性配置和统一格式化接口显示，不能在各面板分别编写换算公式。

### 养成与战斗职责

- `role/`、`equip/`、`skill/` 和升级表通过属性 bean 配置基础属性或成长属性，不在属性表中保存每个对象的实际数值。
- 养成系统负责根据等级、品质、升级和永久加成计算最终基础属性，并生成进入战斗前的属性快照。
- 战斗系统把属性快照写入自己的属性组件；技能、增益和临时效果只修改战斗运行时加成，不回写静态配置或养成数据。
- 战斗结束后只回传业务明确允许持久化的结果，不能把临时属性加成保存为角色基础属性。
- 系统养成界面与战斗界面读取同一个属性名称和格式定义，避免同一属性显示单位不一致。

### 扩展边界

- 公共属性目录只包含系统养成与战斗共同使用的稳定属性，不能把所有战斗公式输入都集中到 `EAttributeType`。
- 只用于单个玩法内部状态机的计时器、动作窗口、动画速度或相机参数，应留在 `cfg/battle/`、`cfg/skill/` 或对应玩法目录。
- 伤害类型、攻击阶段、武器类别等战斗分类不是公共属性；若只被战斗使用，应由战斗专属 enum、bean 或 config 表达。
- 属性计算公式、伤害公式、战力公式和属性优先级属于运行时规则，不写进属性元数据表，除非项目明确采用可配置公式系统。

当原本只在战斗使用的数值后来需要与系统养成挂钩时，按正式迁移处理：

1. 在 `EAttributeType` 中分配新的稳定枚举值，并在 `attribute.xlsx` 补齐名称、描述和数值格式。
2. 把角色、装备、技能或升级配置中的养成来源接入该属性，明确基础值与成长值的合成顺序。
3. 把战斗读取改为消费养成生成的属性快照，不再同时读取旧战斗字段，避免双重生效。
4. 检查存档、网络数据、配置生成代码、运行时映射和用户界面格式化的兼容性。
5. 旧枚举值不得复用；旧战斗字段确认没有调用方后再删除。

## `cfg/item/`

### 文件职责

| 文件 | 内容 |
| --- | --- |
| `cfg/item/item.xml` | 定义品质、物品类型、物品信息和相关 config |
| `cfg/item/item.xlsx` | 配置物品静态数据 |
| `cfg/item/quality.xlsx` | 配置品质对应的通用展示资源 |

### 品质配置

品质枚举只表达有序稀有度。`Quality` config 可以保存颜色、背景、边框等跨界面展示资源 ID。

攻击倍率、掉落概率、升级成长等玩法数值不能放在通用品质表，应由对应玩法目录配置。

### 物品配置

`Item` 最少包含物品 ID、物品类型、名称或本地化 key、描述、图标和可选品质。

- 类型独有数据使用多态 `ItemInfo` 或独立业务配置。
- 数量、拥有状态、过期时间和锁定状态属于用户运行时数据。
- 装备、角色、礼包等复杂玩法通过独立表关联物品 ID，公共物品表不复制完整玩法属性。

为避免 `Item` 与 `Bonus` 互相引用形成循环依赖，礼包开启奖励等关系优先放到独立业务关联表或运行时映射中，不让物品基础表反向依赖奖励模块。

## `cfg/bonus/`

### 文件职责

| 文件 | 内容 |
| --- | --- |
| `cfg/bonus/bonus.xml` | 定义 `Bonus` 多态父 bean 和 `BonusData` config |
| `cfg/bonus/bonus.xlsx` | 配置可复用奖励组合 |

### 通用配置

通用奖励子类型可以包含：

- 空奖励。
- 货币奖励。
- 物品奖励。
- 多项组合奖励。
- 引用另一条奖励配置。
- 随机或带权重的奖励组合。
- 重复生成或复制发放。

奖励配置只描述结果。随机种子、发放事务、背包容量、补偿邮件和重复领取保护由运行时奖励服务负责。

角色、装备、战斗或竞技场特有奖励通过业务层配置或运行时适配器扩展，公共奖励模块不能反向依赖具体玩法类型。

## `cfg/user/`

`cfg/user/` 保存用户系统启动所需的静态默认配置和可复用展示档案。它只描述“新用户如何初始化”和“可选择的静态用户资料”，不保存某个玩家当前拥有的数据。

### 文件职责

| 文件 | 内容 |
| --- | --- |
| `cfg/user/user.xml` | 定义 `User` 单行 config、`Head` 等用户静态 config，以及相关 enum、bean |
| `cfg/user/user.xlsx` | 配置默认名称、初始头像、初始公共数值和初始奖励等新用户默认值 |
| `cfg/user/head.xlsx` | 配置头像 ID、图标、背景或其他跨界面展示资源 |

### 通用配置

- `User` 推荐使用 `mode="one"`，只保存所有新用户共享的初始化默认值。
- 初始头像通过 `ref="head"` 引用 `Head`，初始奖励通过公共奖励 bean 引用 `cfg/bonus/`，展示资源通过稳定资源 ID 引用 `cfg/asset/`。
- `Head` 使用稳定 ID，头像图标、背景框等静态展示数据放在配置表；玩家当前选择的头像 ID 属于用户存档。
- 用户名、当前货币、当前积分、账号等级、登录状态和已领取记录属于运行时或存档数据，不能写回 `user.xlsx`。
- 创建账号、保存数据、云同步、改名校验和奖励发放由用户系统运行时代码负责，配置只提供初始化输入。

### 扩展边界

只有多个系统都需要读取的用户初始化值或用户展示档案才放在 `cfg/user/`。某个玩法自己的初始分数、段位或卡组规则应留在对应玩法目录，并由创建流程组合，不能因为最终写进用户数据就全部堆入 `User` 单行表。

## `cfg/function/`

`cfg/function/` 保存跨界面、跨系统复用的功能标识和结构化跳转信息，使按钮、活动、引导和消息入口通过稳定 ID 请求功能，而不是在配置或用户界面代码中硬编码面板路径和业务调用链。

### 文件职责

| 文件 | 内容 |
| --- | --- |
| `cfg/function/function.xml` | 定义功能 enum、跳转信息多态 bean 和 `Jump` config |
| `cfg/function/jump.xlsx` | 配置跳转 ID、策划说明和具体跳转参数 |

### 通用配置

- 功能枚举使用稳定值表达可被多个系统引用的功能类型，删除后不复用旧值。
- `JumpInfo` 使用父 bean 加子 bean 表达不同跳转类型；每个子 bean 只保存执行该跳转所需的数据。
- `Jump` 使用稳定 ID，运行时由统一功能或跳转服务读取配置并执行。
- 用户界面、引导、活动和推送只发起跳转请求，不自行解释其他模块的内部节点路径。
- 跳转前的开放条件可以引用公共 `Condition`，但条件检查必须保持只读；资源扣除、奖励发放和广告回调等副作用由对应运行时服务完成。

### 扩展边界

配置可以描述“跳到哪里”和“需要哪些参数”，不能替代业务权限、网络校验、下载检查或场景生命周期。只被单个玩法内部使用的状态切换留在该玩法代码或配置中，不为它创建全局功能 ID。

## `cfg/guide/`

`cfg/guide/` 保存新手引导和功能教学需要的静态内容。引导入口、步骤推进、事件监听和完成状态由统一引导管理器负责，配置表不直接控制用户界面或战斗对象。

### 文件职责

| 文件 | 内容 |
| --- | --- |
| `cfg/guide/guide.xml` | 定义 `Guide` config 及稳定后可复用的引导参数 bean |
| `cfg/guide/guide.xlsx` | 按引导 ID 配置有序文本、步骤参数和策划说明 |

### 通用配置

- `Guide.id` 是稳定的大阶段或引导流程 ID；每个流程的文本和参数按实际步骤顺序配置。
- 文本可以直接保存中文，也可以在项目启用本地化后改为语言 key；同一项目必须采用一致规则。
- `dialog` 等有序数组只保存静态文本，`guideParams` 只保存步骤需要的静态参数。
- 参数结构已经稳定、类型明确时，优先从字符串数组升级为有字段注释的 bean，避免运行时到处按下标解析。
- 当前步骤、计数进度、是否完成、是否领奖和中断恢复位置属于引导运行时数据或用户存档，不写入静态配置。

### 运行时边界

- 统一引导管理器读取 `Guide` 配置，负责入口判断、步骤推进、完成记录和异常恢复。
- 用户界面只提供高亮、遮罩、对话和任务显示接口，并通过事件或回调通知引导管理器。
- 战斗、关卡等业务模块只发送命中、拾取、状态变化等普通业务事件，不直接引用引导脚本。
- 引导配置可以引用功能跳转 ID，但 `cfg/function/` 不能反向依赖具体引导步骤。
- 引导奖励引用公共奖励配置，实际发放必须经过统一奖励服务并具备防重复领取保护。

## `cfg/battle/`

`cfg/battle/` 保存只在战斗运行时使用的专属配置。该目录属于玩法层，不是公共配置层；它可以引用 `cfg/common/`、`cfg/attribute/`、`cfg/asset/` 等公共能力，公共目录不能反向引用它。

下面的文件名是推荐职责划分。接入已有项目时优先沿用已经存在的同类文件，例如项目已经使用 `battleAsset.xml / battleAsset.xlsx` 时继续在该文件维护战斗资源，不为统一命名重复建表。

### 文件职责

| 文件 | 内容 | 是否必需 |
| --- | --- | --- |
| `cfg/battle/battleAsset.xml` | 定义战斗资源类型、资源信息 bean 和战斗资源 config | 战斗使用独立资源索引时需要 |
| `cfg/battle/battleAsset.xlsx` | 配置战斗资源 ID、资源类型、路径和资源参数 | 与 `battleAsset.xml` 配套 |
| `cfg/battle/battleGlobal.xml` | 定义战斗固定规则的单行 config，推荐使用 `mode="one"` | 存在跨战场共用的固定战斗规则时需要 |
| `cfg/battle/battleGlobal.xlsx` | 配置战斗时长、动作窗口、状态恢复、战斗开关等全局规则 | 与 `battleGlobal.xml` 配套 |

项目生成器习惯使用单个模块 XML 时，可以把上述定义合并到已有的 `cfg/battle/battle.xml`；拆分或合并必须服从目标项目真实结构，不能同时保留两套重复 config。

### 战斗专属配置边界

- 战斗阶段、命中窗口、格挡恢复、局内冷却、战斗相机、动画表现和战场判定等只服务战斗流程的数据放在 `cfg/battle/`。
- 一组全局固定参数优先使用 `battleGlobal.xlsx` 的明确字段，不要为了统一读取方式把所有参数包装成属性。
- 战斗专属数值直接使用含义明确的字段或 bean，放进 `battleGlobal` 或拥有该规则的战斗业务 config；不单独建立 `battleAttribute` 表，也不能冒充公共 `EAttributeType`。
- 如果某个属性会被角色等级、装备升级或其他系统养成永久改变，并作为基础值传入战斗，它必须定义在 `cfg/attribute/`，战斗只读取养成生成的属性快照。
- 战斗专属配置不能保存玩家永久成长结果，也不能在战斗结束后直接回写公共属性配置。

### 运行时读取

- 战斗创建阶段读取系统养成传入的公共属性快照。
- 战斗规则系统读取 `battleGlobal` 等战斗专属配置，并把固定参数初始化到对应运行时组件。
- 战斗中的技能、增益和临时变化写入运行时状态，不修改 xlsx 数据。
- 某个战斗专属属性后来需要与系统养成挂钩时，按 `cfg/attribute/` 章节的迁移步骤提升为公共属性，并清理旧战斗字段，避免同一数值生效两次。

## 不属于通用配置的目录

下列目录默认属于具体玩法，不纳入项目框架通用配置：

| 目录 | 典型职责 |
| --- | --- |
| `cfg/role/` | 角色、角色成长和角色资源 |
| `cfg/equip/` | 装备、装备类型和装备成长 |
| `cfg/skill/` | 技能、效果、子弹和增益 |
| `cfg/battle/` | 战斗资源、战斗规则、战斗专属属性或战场配置；具体边界见上方 `cfg/battle/` 章节 |
| `cfg/arena/` | 竞技场、匹配、AI 和段位配置 |

这些目录可以引用通用配置，但通用目录不能引用它们。某项玩法数据确实被多个项目模块稳定复用时，先确认语义和所有权，再制定独立迁移方案，不能直接移动字段制造兼容问题。

## 循环依赖处理

- 公共目录不能引用玩法目录。
- 公共父 bean 只保留稳定基础能力，不写死具体玩法子类型。
- 业务模块通过外键、独立业务 bean、独立关联表或运行时适配器使用公共能力。
- 出现双向引用时，把关联关系移动到更高层的独立业务表，保持基础目录单向依赖。
- 已有项目存在历史循环依赖时，不借普通需求顺手重构；先记录生成器限制、使用方和迁移成本。

## 新项目建立顺序

1. 创建 `cfg/cfg_sc.xml` 和必要的 `cfg/common.xml` 基础值对象。
2. 按实际能力创建 `cfg/global/`、`cfg/asset/`、`cfg/sound/`、`cfg/localize/` 和 `cfg/error/`。
3. 系统养成和战斗需要共享属性时，创建 `cfg/attribute/`，统一属性 ID、数值格式和展示元数据；战斗独有数值直接留在后续创建的 `cfg/battle/` 专属配置中。
4. 项目存在经济系统时，再创建 `cfg/common/` 与 `cfg/item/`。
5. 多个模块确实共享奖励能力时，再创建 `cfg/bonus/`。
6. 需要用户初始化、统一功能跳转或新手引导时，依次创建 `cfg/user/`、`cfg/function/` 和 `cfg/guide/`。
7. 最后接入角色、装备、技能、战斗和其他玩法目录；战斗专属规则统一落在 `cfg/battle/`。
8. 每新增一个目录都执行配置生成、编译和最小运行时读取验证。

## 审查清单

- 每个 XML 和 xlsx 是否位于职责对应的目录。
- 总入口 include 路径、顺序和模块依赖是否正确。
- 公共目录是否反向引用了玩法目录。
- 资源路径、音频路径和展示文本是否仍被业务代码硬编码。
- `global.xlsx` 是否堆入了本应放在玩法 `mode="one"` 表的参数。
- `Item`、`Cost`、`Condition` 和 `Bonus` 是否形成循环依赖。
- `user.xlsx` 是否只保存新用户默认值，玩家当前数据是否仍由存档或服务端维护。
- 功能跳转是否通过稳定 ID 和统一服务执行，而不是在配置中硬编码界面对象或业务调用。
- 引导配置是否只保存静态文本和参数，步骤进度、完成状态及事件监听是否仍由引导管理器负责。
- `EAttributeType` 中的每个属性是否确实需要在系统养成与战斗之间共享。
- 战斗独有的计时、动作窗口、判定或表现参数是否被误放进了公共属性表。
- 战斗专属配置是否统一放在 `cfg/battle/`，且没有与公共属性或系统养成字段重复生效。
- 养成和战斗是否使用同一属性 ID、数值单位和格式化规则。
- 战斗临时属性是否与养成基础属性分开保存，且不会反向污染静态配置。
- 配置是否只描述数据，事务、随机、校验和副作用是否仍由运行时服务负责。
- 文档和配置中是否混入当前项目的业务 ID、测试值或临时类型。

# 09. 跨项目通用 Onboarding 模板

## 1. 这份模板是做什么的
- 这是一份可以复用到后续项目里的新人接入模板。
- 它不依赖当前游戏的具体玩法，只保留“AI 协作开发”中已经验证有效的通用结构。
- 新项目开始时，可以直接复制这份模板，再替换项目名、目录、技术边界和示例文档路径。

## 2. 适合什么项目
- Unity 小游戏项目
- 有明确脚手架或工程规范的项目
- 需要长期和 AI 协作开发的团队

## 3. 新项目建议保留的 6 个 onboarding 章节

### 3.1 项目入口
说明：
- 告诉新人这个项目的开发入口、运行入口、核心目录分别在哪里。

建议内容：
- 项目启动方式
- 主要业务代码目录
- UI 目录
- 配置目录
- 文档目录

### 3.2 AI 与开发人员职责分工
说明：
- 这是最值得保留的一章。
- 新人如果一开始搞不清 AI 和开发人员分别负责什么，后面协作成本会很高。

建议内容：
- AI 负责：分析、设计、实现、整理
- 开发人员负责：确认、创建、调整、验证、反馈

### 3.3 需求整理优先级
说明：
- 需求不清时，不要直接进入代码开发。
- 先进入“需求整理与需求落地”阶段。

建议内容：
- 什么情况下先整理需求
- 什么时候才适合正式进入编码
- 需求整理阶段的产出物

### 3.4 开发协作流程
说明：
- 让新人知道标准工作流是什么。

建议内容：
1. 提出目标
2. 整理需求
3. 判断归属层
4. 出最小改动方案
5. 手动创建显示对象
6. 编码实现
7. 联调修正
8. 规则沉淀

### 3.5 常见问题与错误案例
说明：
- 这章对新人非常有价值。
- 不一定要很多，但最好保留 5-10 个真实案例。

建议内容：
- Prefab 绑定没 Apply
- 初始化刷新和轻刷新混用
- 模块直接碰 UI
- 文档口径没同步
- 把有职责的对象误做成普通 Item

### 3.6 提问模板与反馈模板
说明：
- 这是最容易复用的一章。
- 新项目只要把里面的路径和文件名替换掉，就能直接用。

建议保留模板类型：
- 新需求，先不要写代码
- 新需求，进入需求整理模式
- 需求已明确，进入正式开发
- 编译错误反馈
- 运行时错误反馈
- UI 现象反馈
- 开发检查
- 项目全局规则

## 4. 新项目建议直接复制的 4 条核心原则

### 原则 1
- 需求整理与需求落地优先于代码开发

### 原则 2
- 显示对象必须先由开发人员手动创建，AI 再继续依赖这些对象写代码

### 原则 3
- `Module / System` 不直接操作显示对象，统一通过事件驱动 `Panel / View`

### 原则 4
- 已经被证明可跨项目复用的经验，要及时沉淀成项目全局规则

## 5. 新项目落地时建议替换的内容
- 项目名
- 技术规范文件路径
- 需求文档路径
- 开发方案路径
- 主要业务目录
- API 文档目录
- 当前脚手架专有名词

## 6. 推荐的跨项目首页结构
新项目的 `developer-helper/README.md` 建议保留这种结构：
- 手册定位
- 先看哪一章
- 关键原则
- 职责分工图
- 协作总流程图
- 目录说明

## 7. 推荐的跨项目提示词模板

### 模板 A：新项目的首次玩法需求整理
```txt
你现在先不要写代码，先进入“需求整理与需求落地”模式。

我会先给你一版初始玩法输入，请你帮我逐步整理成开发可直接使用的需求文档。

输入如下：
1. 游戏主场景示意图：
2. 核心玩法描述：
3. 单局目标：
4. 当前已知规则：
5. 参考产品（如果有）：
6. 当前优先想细化的部分：

要求：
1. 先整理核心玩法骨架。
2. 每轮只问最关键的一批待确认问题。
3. 需求文档持续更新。
4. 需要界面表达的内容同步输出 SVG 草图。
5. 当前阶段先不进入代码开发。
```

### 模板 B：新项目的正式开发协作
```txt
现在需求协作已经基本完成，下面进入正式开发协作阶段。

已知信息如下：
1. 技术规范：
2. 需求文档：
3. 当前开发目标：
4. 是否涉及新的 UI / Prefab / Panel：
5. 当前哪些对象已经存在：
6. 当前我希望你先做的事情：

你的工作要求：
1. 先判断需求归属层。
2. 先给我最小改动方案，再开始改代码。
3. 如果需要新增显示对象，先暂停并列出需要我手动创建的对象清单。
4. 如果发现已有同名脚本，先暂停并告诉我，优先复用已有脚本。
5. 代码实现时遵守当前项目脚手架、事件驱动、日志和注释规则。
```

## 8. 一句话建议
- 新项目不要从零重新摸索协作方式，直接复制一套已经验证过的 onboarding 结构，再按项目特点替换细节。

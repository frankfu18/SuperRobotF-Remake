# 数据与本地存档

## 数据权威来源

默认采用本地存档，但实现前必须确认目标项目是本地权威、服务端权威还是混合模式。服务端权威项目中，本地数据只能按现有协议作为缓存，不能再建立一份可独立修改的本地真值。

## 持久化模型

- 使用目标项目现有强类型 Root 数据和序列化框架。
- 集合、字典和嵌套对象在定义或反序列化后保证非空。
- 只保存无法从配置和其他真值重建的数据。
- 红点、可升级、总属性等可推导结果默认不保存。
- ID、等级、数量和时间使用项目统一类型，避免同一含义多种数值类型混用。
- 运行时缓存必须能在登录或重载后从持久化数据重新构建。

## 统一写入口

业务代码只通过数据库门面或 Module 修改数据：

1. 获取当前玩家数据。
2. 完成业务校验。
3. 构造一次事务的全部变更。
4. 原子提交到内存真值。
5. 标记脏数据或调用统一保存入口。
6. 保存成功或按项目约定提交成功后发送事件。

禁止 UI、MonoBehaviour 或临时工具直接写磁盘文件。频繁操作应复用项目现有的帧末合并保存或批量提交机制。

## 新用户初始化

新用户初始化必须幂等：重复调用、登录重试和异常恢复都不能重复发放初始资源。

- 使用明确的初始化版本、完成标记或稳定记录判断，而不是依赖货币为零等合法业务值。
- 默认角色、装备、物品和货币先完整校验，再一次性写入。
- 初始化中途失败时不得留下“发了一半”的账号。
- 初始化成功后记录版本，并通过统一保存入口持久化。

## 旧档迁移

每次修改持久化结构都必须记录：

- 旧版本识别方式。
- 新字段默认值来源。
- 字段重命名、类型变化和数据转换规则。
- 重复执行迁移是否安全。
- 迁移失败时的日志、回退和是否阻止登录。
- 迁移完成版本何时写入。

迁移按版本顺序逐级执行，不能只为最新旧档写一条临时判断。删除字段前先确认旧版本读取和回滚要求。

## 异常与恢复

- 反序列化失败按目标项目规则备份、上报或阻止覆盖，不能直接用空档覆盖损坏档案。
- 提交过程中抛出异常时恢复事务前状态，或依赖数据库事务能力回滚。
- 保存失败不能发送会让 UI 误判成功的事件。
- 数量溢出、负数、未知 ID 和非法等级必须在写入前拒绝。
- 调试修复工具也必须走同一校验和保存链路，并记录来源原因。

## 验证重点

- 保存后重启能恢复角色、装备、货币、物品和上阵状态。
- 新用户初始化重复执行不重复奖励。
- 旧档缺字段时能补默认值，不丢失已有资源。
- 任意一步失败时不会出现部分扣除、部分升级或事件先于保存。

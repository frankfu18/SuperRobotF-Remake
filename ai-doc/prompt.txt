【项目事实（必须遵守）】
1. Unity版本以 `ProjectSettings/ProjectVersion.txt` 为准：`6000.0.75f1`。
2. 构建入口场景是 `Assets/Scenes/Main.unity`（`EditorBuildSettings.asset` 已配置）。
3. 运行入口：`GameRoot : GameEntry`。
4. 启动流程由 `GameLauncher + GameLaunchProcedure` 驱动：
   - 静态流程（框架）：`StartUp -> CheckVersion(可选) -> CheckPackageAssets/CheckHotfix/ResolveAssets`
   - 业务自定义流程（GameRoot中注册）：`SystemInitProcedure -> FontLocalizationProcedure -> HotUpdateProcedure -> LoginProcedure`
5. 基础系统管理器：`SystemManager`，已内置系统顺序：

6. 热更入口：`HotUpdateSystem.LoadHotUpdateAssembly()` 反射调用 `HotUpdateMain.Run/Login/Logout`。
7. 业务代码主落位在 `Assets/HotUpdate`；框架核心在 `Assets/FrankGame/Framework`；通用宿主系统在 `Assets/Scripts`。

【本地数据库开发硬规范（新Database组件）】
1. 初始化入口统一使用 `DatabaseBootstrap.Initialize()`（可幂等重复调用）。
2. 业务读写统一通过 `DatabaseHelper.Instance.Get/Update/TryCheck`；禁止直接读写数据库落盘文件。
3. 写操作必须放在 `Update<TRoot>(...)` 回调中，禁止绕过 `Update` 直接改 Root 后不标脏。
4. Root 模型必须实现 `IDataRoot`，并可被默认构造（无参构造）。

【数值配置全链路（补充）】
1. 定义入口
   - `cfg/cfg_sc.xml` 是客户端配置定义聚合入口，通过 `<include>` 汇总各业务配置定义（如 item/global/guide 等）。
   - 每个子配置由 `xml` 定义结构与字段，并绑定对应 `excel` 数据源（`<config input="xxx.xlsx">`）。

2. 生成阶段（策划配置 -> 客户端产物）
   - 配置生成入口：`client/gen_config.bat`。
   - 使用 `perfect.gen.cfg.Main`，输入 `cfg/cfg_sc.xml`。
   - 生成双产物：
     - 二进制配置：`client/Assets/Res/config/*.bytes`
     - 强类型代码：`client/Assets/Perfect/EditorConfig/Gen/cfg/*.cs`（含 `CfgMgr` 与各表类型）

3. 打包与索引阶段
   - `BuildAssetsWindow.BuildConfig` 将 `Assets/Res/config/*.bytes` 打成配置资源并生成配置索引。
   - `MergeTotalIndexFile` 将配置索引合并到总索引（供资源解析与热更使用）。

4. 启动加载阶段（必须满足顺序）
   - 框架静态流程会进入 `ResolveAssetsProcedure`。
   - `ResolveAssetsProcedure` 触发 `BundleManager.LoadTotalConfig` 预加载配置数据。
   - 静态流程完成后进入热更业务入口 `HotUpdateMain.Run`。
   - `HotUpdateMain.Run` 中必须先执行 `ConfigSystem.Init`，由其调用 `CfgMgr.Load` 完成内存化。

5. 运行时读取路径（按资源模式）
   - `ELoadMode.Local`：`ConfigSystem.OnConfigLoad` 直接读取 `Assets/Res/config/*.bytes`。
   - `ELoadMode.AssetBundle/Net`：`ConfigSystem.OnConfigLoad` 通过 `BundleManager.GetConfigData` 读取已加载配置字节。

6. 业务使用规范
   - 业务层统一通过 `ConfigSystem.CurrentData` 访问配置（如 `GetItemList/GetGlobal/GetGuide...`）。
   - 禁止业务代码直接读取 `*.bytes` 文件或绕过 `ConfigSystem/CfgMgr` 自建读取链路。

7. 变更配置的最小闭环
   - 修改 `cfg/*.xml` 定义或 `cfg/*.xlsx` 数据后：
     1) 执行 `client/gen_config.bat`
     2) 重新打包配置资源（必要时合并索引）
     3) 运行验证 `ConfigSystem.CurrentData` 对应表项可读取

8. 新增或修改配置字段的强制同步规则
   - 任何新增或修改 `cfg` 配置字段时，必须同步检查并更新：
     1) `cfg/*.xml` 字段定义
     2) 对应 `cfg/*.xlsx` 数据列
     3) 生成类 `client/Assets/Perfect/EditorConfig/Gen/cfg/*.cs`
     4) 运行时配置产物 `client/Assets/Res/config/*.bytes` 的生成流程
     5) 本次功能的执行记录或开发文档
   - 禁止只改 Excel、只改生成类、只改业务代码，或只依赖运行时代码默认值。
   - 如果暂时无法重新生成 `*.bytes`，可以在代码中增加兼容默认值，但必须在结果说明中明确提示后续仍需执行配置生成流程。

【多语言使用流程（补充）】
1. 分层模型（必须区分）
   - 启动文案层（Framework）：用于启动流程提示文本（版本检查、热更、解压等）。
   - 业务文案层（HotUpdate + 配置表）：用于游戏内 UI/业务文本。

2. 启动语言确定流程（Framework）
   - 启动阶段 `StartUpProcedure` 调用 `LocalizationManager.CheckLanguage(...)`。
   - 若配置 `FollowSystemLanguage=true`，按系统语言；否则按默认语言。
   - `LocalizationManager` 优先读取本地缓存（PlayerPrefs），再设置当前语言。

3. 启动文案来源与调用
   - 文案来源：`Assets/Resources/FrankGame/PackageLocalizationTable.xml`。
   - 启动流程文案统一通过 `LocalizationManager.GetPackageLanguageText(key, ...)` 获取。
   - 典型调用点：`CheckVersionProcedure / CheckPackageAssetsProcedure / CheckHotfixProcedure / ResolveAssetsProcedure`。

4. 业务文案加载流程（HotUpdate）
   - `HotUpdateMain.Run()` 中先执行 `ConfigSystem.Init()`。
   - `ConfigSystem.Init()` 内部绑定 `CfgMgr.onLoadConfig` 并调用 `CfgMgr.Load()`。
   - 业务语言表来自配置产物 `Assets/Res/config/language_*.bytes`（由 `cfg/localize/*.xlsx` 生成）。

5. 业务文案读取链路
   - 业务/UI 统一调用 `LanguageSystem.GetLanguage(key, ...)`。
   - `LanguageSystem` 内部调用 `ConfigSystem.GetLanguage(...)`。
   - `ConfigSystem` 最终通过 `ConfigSystem.CurrentData`（`CfgMgr`）读取语言表。

6. 语言切换与缓存
   - 运行时切换：`LanguageSystem.SetLanguage(...)` -> `LocalizationManager.ChangeLanguage(...)`。
   - 缓存写入：`LanguageSystem.SetLanguageCache(...)` -> `LocalizationManager.SaveLanguageCache(...)`。
   - 下次启动会优先使用缓存语言。

7. 当前实现差异（必须知晓）
   - 包内启动文案层支持：中/繁中/英/日/韩/越（按 `PackageLocalizationTable.xml` 节点）。
   - 业务文案层当前 `ConfigSystem.GetLanguage(...)` 仅启用中/英分支；其他语言分支处于注释状态。
   - 因此业务层在未命中时会回退英文，需在扩语言时同步补齐 `ConfigSystem.GetLanguage` 分支实现。

   - SVG 必须使用 UTF-8 编码保存，并在文件头声明 `<?xml version="1.0" encoding="UTF-8"?>`，中文文本不得转成乱码或拼音占位。
   - SVG 中文字体优先使用常见中文字体回退链，如 `Microsoft YaHei`, `PingFang SC`, `Noto Sans CJK SC`, `SimHei`, `Arial Unicode MS`, `sans-serif`。
   - SVG 和字段/组件说明必须先交给用户确认；用户确认没问题后，才能把对应 Panel 方案落地到 `ai-doc/develop-setup`。
   - 在确认前，不得直接编写依赖该 Panel 字段绑定、Prefab 层级或 AutoGen 结果的业务代码。

3. 非滚动容器优先 Layout
   - 如果 `List` 或 `Grid` 不需要滚动，优先使用 Unity 自带 `Layout` 组件。
   - 只有在确实需要滚动、复用列表单元或虚拟化时，才使用 `UIList`。

4. `**Layout` 命名对象初始化规则
   - 如果游戏对象命名符合 `m_GameObject_**Layout`，则默认其挂载 `UILayoutObject` 或对应布局组件。
   - 代码初始化时必须显式调用其 `Initialization(...)`，不能只依赖 Unity 默认生命周期。

5. 模块与显示层解耦规则
   - `Module` 或 `System` 不能直接操作具体 `GameObject / Transform / Panel 字段`。
   - 所有显示驱动都必须通过事件通知 `Panel / View` 层完成。
   - 战斗场景内自有世界表现除外，例如单位 `Animator`、技能特效、飘字、地图资源点表现，可由战斗表现层按战斗事件直接控制。
   - 除战斗场景自有 UI/世界表现外，所有由战斗产生并影响普通 UI `Panel` 的数据变更，必须通过事件驱动解耦，禁止战斗逻辑直接操作其他 `Panel` 字段或实例。

6. 同名脚本优先复用规则
   - 当某个 `GameObject` 需要增加职责逻辑时，先检查项目中是否已存在同名脚本。
   - 若已存在，优先把逻辑放入已有脚本，不新建同类脚本文件；如存在风险或边界不清，先暂停并与用户确认。

7. `TODO-AI` 执行规则
   - 如果代码注释中出现 `TODO-AI`，表示该业务逻辑需要 AI 实现。
   - AI 在实现前必须先给出“具体实现细节”，待用户确认后再编码。
   - 实现完成后，把 `TODO-AI` 改为 `AI-DONE`。

8. 新增脚本日志字段规则
   - 所有新增脚本类，必须在类前部增加统一日志字段：
   - `private readonly LoggerForClass Logger = LoggerForClass.Create(typeof(当前类型));`

9. 关键节点日志规则
   - 在加载、切关、关键状态切换、关键结算、失败分支、异常兜底等关键节点，必须增加必要日志。
   - 日志统一使用 `Logger.Debug(...)` 输出，不混用临时 `Debug.Log(...)`。

10. 类、属性和方法注释规则
   - 所有新增或修改的类、属性和方法，都必须补标准 XML 注释。
   - 类注释必须说明该类型的职责、所属层级、生命周期或使用边界；如果有性能、线程、热更新、对象池、配置依赖等限制，也必须写清。
   - 属性注释必须说明字段含义、单位、取值范围、默认值语义，以及是否允许为空、是否只读、是否来自配置或运行时计算。
   - 方法注释必须说明方法作用、关键参数含义、返回值语义、失败条件、副作用和调用限制；涉及状态修改、事件派发、资源加载、对象池回收、动画播放、规则结算时必须写清副作用。
   - 不能只给复杂方法写注释，简单类、简单公开属性和公开方法也要写。
   - 私有方法如果承载规则算法、动画执行、逻辑分支、异常兜底、资源生命周期或性能敏感逻辑，也必须写注释说明。

11. 中文代码注释规则
   - 新增或修改代码时，应尽量补充中文注释，尤其是规则算法、动画执行、状态切换、关键逻辑分支、异常兜底和资源加载链路。
   - 注释要解释“为什么这样做”和“业务规则是什么”，避免只重复代码字面含义。
   - 涉及 Animator、Tween、特效、UI 状态切换等表现流程时，必须在关键触发点和回调处写清中文注释。
   - 代码文件必须保持 UTF-8 编码，中文注释不得出现乱码、拼音占位或不可读字符。
   - 如果发现已有文件中文注释乱码，不能盲目重写整文件；先定位编码问题和影响范围，再按最小范围修复。

12. 屏幕提示统一规则
   - 如果需求中需要增加屏幕文字提示，统一使用 `FlyTextManager` 实现。
   - 不新增并行的临时弹字方案。

13. 大文件拆分规则
   - 如果某个编辑器脚本、模块脚本或面板脚本变得过大，应优先用 `partial` 或职责拆分方式拆到多个文件中实现。
   - 拆分时保持同一职责域内聚，避免横切混杂。

14. 初始化与轻刷新分离规则
   - 对于运行时 UI 内容，必须区分：
   - 初始化级刷新
   - 局内轻量刷新
   - 切关、重建、布局重算只在初始化级刷新中执行；普通点击、状态切换、局部数据变化只做轻量刷新，避免整块重建。

15. 布局刷新后再做依赖计算
   - 如果某段逻辑依赖 UI 布局后的真实位置或尺寸，则必须在布局刷新完成后，再异步执行后续计算或绘制。
   - 典型场景包括：连线、锚点、路径表现、区域碰撞映射。

16. 先校验再进入实现规则
   - 对一些实现边界复杂、依赖现有代码较重的区域，不能直接接入。
   - 必须先梳理现有实现方式、职责边界、复用点，和用户确认后再继续编码。

17. 新规则先写入规则文档
   - 在项目推进中新增的稳定协作规则，应先沉淀到规则文档，再继续执行。
   - 避免“只在聊天里约定、后续忘记”的情况。

18. `Item` 与自定义组件的选型规则
   - 当元素只是列表/网格中的重复数据单元，且生命周期适合由列表统一管理时，优先使用 `Item + UIList`。
   - 当元素本身有明确业务职责、需要独立状态、需要局部刷新、会被多个区域复用或不适合标准列表管理时，优先做成手动自定义组件，不强行按 `Item` 设计。

19. 项目全局规则触发机制
   - 当用户提到“项目全局规则”或表达类似含义（如“这个能否作为通用规则”“下个项目也适用”“沉淀到全局规则里”）时，必须自动执行以下流程：
   - 先分析当前改动或结论是否与当前游戏业务强相关。
   - 再判断其是否适合抽象为跨项目可复用规则。
   - 将候选规则整理给用户确认。
   - 用户确认后，直接追加到 `prompt.txt`，不再重复确认是否需要修改 `prompt.txt`。

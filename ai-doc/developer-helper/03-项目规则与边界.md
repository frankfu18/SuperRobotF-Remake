# 03. 项目规则与边界

## 1. 项目内必须始终遵守的规则
- 先读 `prompt.txt`
- API 文档优先于源码推断
- 业务代码优先落在 `HotUpdate`
- 不绕开 `SystemManager / ModuleHandler / UISystem`
- 不手改 `AutoGen`
- 不额外套一层平行框架

## 1.1 这一章怎么读

### AI 更需要重点遵守的规则
- 先读 `prompt.txt`
- API 文档优先于源码推断
- 不绕开现有脚手架
- 不手改 `AutoGen`
- 不直接让 `Module / System` 操作显示对象

### 开发人员更需要重点配合的规则
- 及时补齐 Prefab、字段绑定和布局组件
- 反馈真实运行现象，而不是只说“有问题”
- 对关键实现口径及时确认

## 2. UI 相关关键规则

### 2.1 什么时候用 `Item`
- 它只是一个列表/网格中的重复单元
- 生命周期适合交给列表管理
- 职责轻，通常只负责显示和简单点击
- 更像“一个 cell”，而不是“一个功能对象”

### 2.2 什么时候用手动自定义组件
- 元素本身有明确业务职责
- 需要独立状态
- 需要局部刷新
- 会被多个区域复用
- 不适合标准列表管理

### 2.3 判断口诀
- 更像“列表条目”就用 `Item`
- 更像“有职责的视图对象”就做自定义组件

## 3. 事件驱动边界
- `Module / System` 只负责状态和事件
- `Panel / View` 负责显示对象更新
- 业务不要从模块里直接拿 `Transform`
- 复杂表现也先经由事件进入显示层

## 4. 注释和日志规则
- 所有新增脚本类都要有：
  - `private readonly LoggerForClass Logger = LoggerForClass.Create(typeof(当前类型));`
- 关键节点用 `Logger.Debug(...)`
- 所有新增或修改的类、属性和方法都写 XML 注释
- 类注释说明职责、所属层级、生命周期、使用边界和限制
- 属性注释说明含义、单位、取值范围、默认值语义、空值/只读约束和数据来源
- 方法注释说明作用、参数、返回值、失败条件、副作用和调用限制
- 私有方法只要承载规则算法、动画执行、逻辑分支、异常兜底、资源生命周期或性能敏感逻辑，也必须写注释

说明：
- 这部分主要由 AI 在写代码时执行。
- 开发人员需要做的是在联调时利用这些日志快速定位问题。

## 5. 屏幕提示规则
- 需要屏幕提示时，统一使用 `FlyTextManager`
- 不并行维护第二套临时提示方式

## 6. 复杂区域处理规则
- 边界不清时不要直接改
- 先梳理现有实现
- 先确认职责归属
- 再开始落代码

## 7. 典型高风险区域
- 路径表现 / 连线 / 特效挂点
- 自动生成脚本配合区域
- 布局完成后再计算坐标的区域
- 运行时重建和轻刷新混用区域
- 配置与运行时状态互相推导区域

## 8. 配置字段变更规则

新增或修改 `cfg` 配置字段时，不能只改其中一处。必须同步检查：

- `cfg/*.xml` 字段定义
- 对应 `cfg/*.xlsx` 数据列
- 生成类 `client/Assets/Perfect/EditorConfig/Gen/cfg/*.cs`
- 运行时配置产物 `client/Assets/Res/config/*.bytes` 的生成流程
- 当前功能的执行记录或开发文档

如果暂时无法重新生成 `*.bytes`，代码可以加兼容默认值，但交付说明里必须明确提醒后续执行配置生成流程。

## 9. 文档、需求、开发方案三者关系
- `需求文档`
  - 定义业务目标与规则
- `demo-game-setup.md`
  - 定义当前项目落地方案
- `prompt.txt`
  - 定义跨需求、跨阶段、跨项目的开发规则

## 10. 遇到冲突时怎么处理
- 文档与代码冲突：先按文档
- `prompt.txt` 与旧习惯冲突：按 `prompt.txt`
- 本轮新确认规则与旧规则冲突：按最新确认规则
- 业务规则不清：先停下来对齐，不强行猜

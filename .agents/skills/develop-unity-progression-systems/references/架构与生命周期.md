# 架构与生命周期

## 目标

系统养成代码必须把配置、玩家真值、业务规则、跨模块编排、事件和 UI 分开。先识别目标项目已有架构，再将新需求放进现有职责中，禁止为了一个功能新建第二套模块生命周期或数据中心。

## 推荐分层

1. **静态配置层**：描述等级、品质、消耗、奖励和属性规则，不保存玩家状态。
2. **持久化数据层**：保存玩家已拥有、当前等级、已领取、上阵选择等最小真值。
3. **业务 Module 层**：提供查询和命令，完成完整校验、事务修改、保存和事件发送。
4. **跨模块编排层**：处理需要多个 Module 协作的完整用例，例如消耗货币后升级装备。
5. **事件层**：在提交成功后通知 UI、红点或外围系统刷新。
6. **UI 展示层**：读取只读数据，提交业务命令，不直接修改存档对象。

依赖方向只能由上层业务流向稳定的下层能力。配置和公共经济模块不能反向依赖角色、装备、商店或具体玩法。

## 模块生命周期

先从目标项目真实调度器确认生命周期名称和顺序。通常至少覆盖：

- **初始化**：创建运行时容器、注册无数据依赖的服务。
- **配置加载完成**：建立配置索引和跨表校验，不读取尚未登录的玩家数据。
- **登录**：载入或创建玩家数据，执行迁移和默认值补齐。
- **登录完成**：在依赖模块都可用后做跨模块初始化、发送首次刷新事件。
- **登出**：提交未保存数据，解绑玩家级监听，清理会话缓存。
- **释放**：解绑全局监听，释放资源并清空静态引用。

模块注册顺序必须按依赖排列。例如物品、货币等基础经济模块应先于角色、装备和上层玩法模块。循环依赖应通过编排层、事件或只读接口解除，不能靠调整初始化顺序掩盖。

## Module 接口约束

- 查询接口不产生副作用，返回只读视图、值对象或拷贝。
- 修改接口表达完整业务意图，例如“升级装备”，而不是把存档字典暴露给调用方。
- 公开方法的中文注释写清前置条件、配置来源、失败结果、保存和事件副作用。
- 同一业务只能有一个权威写入口；UI、引导和功能入口都调用这个入口。
- 跨模块操作先完成全部校验，再由编排层提交，避免模块 A 已扣除而模块 B 失败。

## 事件边界

- 数据提交成功后再发送事件，失败不发送成功事件。
- 事件参数优先使用稳定 ID、变更前后值和来源原因，不直接传可变存档对象。
- 事件名称表达已发生的事实，例如“装备升级完成”，不要表达模糊命令。
- 注册和注销必须成对出现；玩家级监听在登出时清理，全局监听在释放时清理。
- UI 事件用于刷新展示，不能作为保证核心事务完成的唯一链路。

## function 与 guide 协作

功能入口系统可以判断是否开放并调用养成公开接口；引导系统可以订阅成功事件并推进步骤。养成模块不负责页面跳转、蒙层高亮、引导步骤或引导进度，也不能引用具体面板和引导控制器。

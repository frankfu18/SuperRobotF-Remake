# 新模块从 0 到 1 开发流程

## 适用范围

本流程用于从零创建完整的 Unity 局外养成业务模块。它不用于战斗 ECS System，也不要求目标项目采用某个固定框架。实现时必须先识别目标项目现有配置、存档、Module、事件、UI、日志和构建体系，再从真实源码提炼新模块结构。

窄范围空判断、事件刷新、显示修复或不改变数据链的修改不需要展开全部流程。新增独立业务模块、持久化模型、经济事务、共享属性或战斗快照时必须完整执行。

## 目录

1. 阶段 1：阅读项目规则和策划文档
2. 阶段 2：确定职责、真值和依赖边界
3. 阶段 3：调查真实源码并建立提炼映射
4. 阶段 4：生成并确认系统养成框架方案
5. 阶段 5：设计配置并执行生成
6. 阶段 6：设计持久化 Root 和数据迁移
7. 阶段 7：定义公开查询、命令和结果契约
8. 阶段 8：创建 Module 并接入生命周期
9. 阶段 9：实现原子业务事务
10. 阶段 10：定义事件并完成监听清理
11. 阶段 11：接入 UI、function 和 guide
12. 阶段 12：生成并接入战斗快照
13. 阶段 13：补充注释、日志和项目接入
14. 阶段 14：执行完整验证
15. 阶段 15：输出交付清单

## 总体原则

- 按阶段顺序推进；上一个阶段的检查点未通过，不进入下一阶段。
- 不携带或套用自写 C# 模板；代码骨架从目标项目最接近的真实实现提炼。
- 配置源、玩家真值、业务规则、事件和 UI 分层，UI 不直接修改存档。
- 涉及配置时结合 `$develop-unity-config-tables`；涉及战斗快照时结合 `$develop-unity-ecs-battle`。
- 每个阶段都记录输入事实、修改产物、完成标准和未解决问题。
- 命名和排版优先服从目标仓库现有规范；目标仓库没有明确规则时，使用本流程各阶段给出的默认约定。禁止为了统一风格批量重命名无关旧代码。

## 阶段 1：阅读项目规则和策划文档

**输入与项目事实**

- 用户需求、策划文档、验收规则和明确不做的内容。
- 目标仓库的 `AGENTS.md`、`ai-doc`、`docs`、配置规范、存档文档和构建说明。

**工作内容**

- 把需求拆成玩家操作、成功结果、失败结果、持久化影响和外围系统协作。
- 标记仍会改变数据结构、事务或公开接口的待确认项。

**代码规范与命名规则**

- 此阶段先统一领域术语，不急于创建类名。为每个核心概念确定唯一英文名，后续配置、数据、Module、事件和 UI 均复用同一词根。
- 方案文件名使用项目既有规则；无约定时使用 `<domain>-progression-design.md`，其中 `<domain>` 使用简短、稳定的英文领域名。
- 避免 `NewSystem`、`CommonData`、`OtherManager` 等无法表达职责的名称，也不要在正式类型名里使用策划临时编号。

**完成标准**

- 能清楚描述模块目标、范围、成功标准、受众和约束。
- 所有高影响歧义已从文档、源码或用户确认中消除。

**常见错误**

- 未读项目文档就按个人习惯设计框架。
- 只记录正常流程，没有失败、重复请求和重启恢复规则。

## 阶段 2：确定职责、真值和依赖边界

**输入与项目事实**

- 当前配置模块、公共经济模块、功能入口、引导、UI 和战斗边界。
- 数据权威来源是本地、服务端还是混合模式。

**工作内容**

- 明确新模块拥有的玩家真值、可推导缓存和只读输出。
- 列出依赖模块、被依赖者、跨模块编排和禁止反向依赖。
- 判断是否需要配置表、持久化、奖励消耗、共享属性或战斗快照。

**代码规范与命名规则**

- 业务域统一使用 `<Domain>` 词根；业务模块默认命名为 `<Domain>Module`，只有跨领域流程所有者才使用 `<UseCase>Coordinator` 或项目已有编排类型后缀。
- `Module` 表示局外业务域，`System` 表示全局或框架能力，`Manager` 只用于确实管理一组对象及其生命周期的实现；禁止三个后缀混用。
- 数据真值、运行时缓存和展示模型使用不同名称，分别建议为 `<Domain>Data`、`<Domain>Cache`、`<Domain>ViewData`，不能都叫 `<Domain>Info`。
- 布尔概念使用 `Is`、`Has`、`Can`、`Should` 或 `Need` 表达语义；数量使用 `Count`，稳定标识使用 `Id`，避免 `Flag1`、`Value2`。

**完成标准**

- 每个字段和规则都有唯一所有者。
- 新模块不会与现有模块、数据库或事件系统形成第二套真值。

**常见错误**

- 把配置默认值和玩家当前状态放在同一数据层。
- 把红点、总属性等可推导结果作为持久化真值。

## 阶段 3：调查真实源码并建立提炼映射

**输入与项目事实**

- 最接近的新旧 Module、持久化 Root、事件、UI 和测试实现。
- 生命周期基类、模块调度器、数据门面、配置访问器和日志方式。

**工作内容**

- 为每类待建代码记录“来源文件、保留职责、移除业务、替换依赖、待确认项”。
- 确认目标项目是否自动发现存档类型、自动维护项目文件或生成 Unity `.meta`。

**代码规范与命名规则**

- 文件名必须与主要公开类型同名；一个文件默认只放一个主要公开类，紧密依附且只在本文件使用的小类型可按项目风格内聚。
- 命名空间、访问修饰符、字段前缀、参数前缀和花括号风格全部继承参考源码；目标项目使用全局命名空间时，不为单个新模块擅自引入新命名空间。
- 提炼记录使用真实类型名，不使用“某模块”“XXXData”等占位符进入最终方案。
- 接口名使用 `I` 前缀，抽象基类使用能表达职责的 `Base` 后缀；没有多实现需求时不要为每个类机械创建接口。

**完成标准**

- 新模块每个结构性文件都有真实参考来源或明确的项目规范依据。
- 不需要凭空发明第二套 Module、数据库、事件或结果类型。

**常见错误**

- 复制整个旧模块后只改类名，遗留旧业务和事件。
- 为了图快手改生成文件或绕过项目注册机制。

## 阶段 4：生成并确认系统养成框架方案

**输入与项目事实**

- 前三个阶段的需求、职责和源码调查结果。
- `assets/系统养成框架方案模板.md`。

**工作内容**

- 写清配置、持久化模型、Module、公开接口、事务、事件、UI、迁移、战斗快照和测试。
- 按项目约定保存方案；没有约定时使用 `docs/progression/`。
- 把会改变实现的问题集中写入“待确认项”。

**代码规范与命名规则**

- 方案中首次出现类型时写完整候选名和职责，例如 `<Domain>Module`、`<Domain>Data`、`<Action>Result`，避免只写“新增一个类”。
- 公开 API 必须给出方法名、参数语义和返回类型；仍未确认的名称明确标记为待确认，不能同时给出多个候选让实现者临场选择。
- 图表和时序中的节点名称与最终代码类型保持一致，事件名称写出发送方、时机和参数。
- 缩写只使用项目已经广泛采用的形式；新领域词优先写完整单词，避免不同文件出现多种缩写。

**完成标准**

- 方案达到其他工程师无需再次做架构决策即可编码的程度。
- 方案得到用户确认，或所有实现决策已有明确依据。

**常见错误**

- 方案只列文件，没有数据流、事务顺序和失败处理。
- 待确认问题未解决就开始创建持久化结构。

## 阶段 5：设计配置并执行生成

**输入与项目事实**

- 策划数据、字段单位、默认值、引用关系和目标项目配置规范。
- 同模块或同类型的真实 XML、xlsx 和生成流程。
- `$develop-unity-config-tables` 的 `SKILL.md` 及本阶段需要的配置参考文档。

**工作内容**

- 先读取 `$develop-unity-config-tables` 的主入口，确认目标项目配置目录、XML/xlsx 规范、生成脚本和验证要求，不能只引用 Skill 名称而跳过其流程。
- 根据任务内容读取配置 Skill 的对应参考文档：模块与公共配置读取 `references/项目框架通用配置.md`，XML 结构读取 `references/配置表结构规范.md`，xlsx 数据读取 `references/Excel数据规范.md`，生成接入读取 `references/配置生成与代码接入.md`，交付前读取 `references/配置验证清单.md`。这些路径均相对于 `$develop-unity-config-tables` Skill 目录。
- 按配置 Skill 的工作流定义 enum、bean、config 和 xlsx 数据；已有表必须先读取真实 XML 与工作簿，不凭字段名猜测展开结构。
- 写清字段含义、单位、等级 key、默认值来源和异常兜底。
- 执行项目真实配置生成，确认生成类型、访问接口和旧产物清理。

**代码规范与命名规则**

- XML 类型名使用 `PascalCase`；枚举默认使用 `E<Domain><Meaning>`，bean 使用能表达数据结构的名词，config 使用业务对象名。
- xlsx 字段名和 XML `var name` 必须完全一致，并服从项目字段风格；无约定时使用 `camelCase`。
- 引用字段以 `Id` 结尾，多个 ID 使用 `Ids`；列表使用复数名，映射使用 `<Value>By<Key>` 或项目既有 `Map/Dict` 规则。
- 名称必须体现单位：`DurationSeconds`、`Timestamp`、`Ratio`、`Percent`、`Count`。Ratio 或定点数的缩放规则必须写入中文注释。
- 不使用 `data1`、`param2`、`valueList` 等弱语义字段；多态 bean 名称应体现具体业务类型。

**完成标准**

- 源配置可生成，运行时代码能通过稳定接口读取。
- 配置引用、中文、列展开和数据完整性检查通过。
- 已执行配置 Skill 要求的源表检查、生成、运行时接入和配置验证，未执行项有明确原因。

**常见错误**

- 先写运行时代码再猜配置字段。
- 手改生成 C#，或把玩家当前等级、余额、领取状态写进配置表。

## 阶段 6：设计持久化 Root 和数据迁移

**输入与项目事实**

- 目标项目 Root 模型、`[DatabaseRoot]`、`[DataBase]`、Parser 生成器、自动保存和版本机制。
- 新用户默认数据、旧档版本、服务端权威规则，以及已有 `DataModel / AutoGen / ParserExtend` 示例。
- 当目标 Unity 项目包含下述目录和菜单时，按本阶段的当前框架流程执行；其他项目先找到等价目录与生成器，不要机械创建同名路径。

**工作内容**

- 在 Unity 项目根目录的 `Assets/HotUpdate/DataBase/DataModel/` 创建 `<Domain>Data.cs`，定义数据库 Root 和需要持久化的强类型子数据。
- 等待 Unity 完成脚本编译后，执行菜单 `PeekabooGame/DBParser生成`。生成器会扫描 `[DatabaseRoot]` 和 `[DataBase]` 类型，并在 `Assets/HotUpdate/DataBase/AutoGen/` 生成对应的 `*Parser.AutoGen.cs`。
- 确认 Root 生成 `Assets/HotUpdate/DataBase/AutoGen/<Domain>DataParser.AutoGen.cs`；每个带 `[DataBase]` 的子数据也应生成 `<BeanName>Parser.AutoGen.cs`。
- 禁止修改 `AutoGen` 文件。需要补充数据库读取、写入、增删、查找和迁移操作时，在 `Assets/HotUpdate/DataBase/ParserExtend/` 创建 `<Domain>DataParser.cs`，通过 `partial class` 扩展生成的 Parser。
- 设计幂等的新用户初始化、逐版本迁移、默认值补齐和失败回退；集合、字典和嵌套数据在定义或 Parser 加载后保证可安全访问。

### 阶段 6.1：创建 DataModel

Root 类型使用以下结构约定：

```csharp
using System;
using System.Collections.Generic;
using db.core;

namespace db.cfg
{
    [Serializable, DatabaseRoot]
    public class <Domain>Data
    {
        // 只保存无法由配置和其他真值重新推导的玩家数据。
    }
}
```

- Root 必须位于 `db.cfg` 命名空间，使用 `[System.Serializable, DatabaseRoot]`，类名固定为 `<Domain>Data`。
- 需要独立 Parser 的嵌套对象使用 `[System.Serializable, DataBase]`，类型名使用 `<Domain>Info`、`<Domain>Record` 或明确业务名。
- 生成器只扫描 `public` 实例字段；属性、私有字段和未标记的普通引用类型不会按当前规则生成数据库访问代码。
- Root 和子数据应保持无参可创建。字段只保存持久化真值，不放 Unity 对象、运行时回调、资源引用或可推导 UI 状态。

### 阶段 6.2：当前生成器支持的字段类型

| 类型 | 支持方式 | 使用要求 |
|---|---|---|
| `int` | 直接生成可保存属性 | 用于 ID、等级、次数等整数 |
| `long` | 直接生成可保存属性 | 用于大数量和时间戳 |
| `string` | 直接生成可保存属性 | 允许空值时写清业务含义 |
| `bool` | 直接生成可保存属性 | 字段名使用 `is/has/can` 语义 |
| `float` | 直接生成可保存属性 | 不用于要求精确结算的货币数量 |
| `enum` | 按枚举完整类型生成属性 | 枚举调整数值时必须考虑旧档兼容 |
| `List<T>` | 生成 `MonitorList<T>` 或 `ListParser<T>` 访问 | 元素为复杂类型时必须使用 `[DataBase]` 类型 |
| `Dictionary<TKey,TValue>` | 生成 `MonitorDictionary` 或 `DictionaryParser` 访问 | 复杂 value 必须使用 `[DataBase]`；需要子 Parser 的字典优先使用 `int` 等稳定基础类型作为 key |
| `[DataBase]` 子数据 | 生成 `<BeanName>Parser.AutoGen.cs` | 必须可创建并使用 `public` 字段 |

- 当前 `TypeMapping` 明确包含 `int / long / string / bool / float`，并单独处理 enum、`List<>`、`Dictionary<,>` 和 `[DataBase]` 类型。
- 不要直接使用尚未验证的 `double`、`decimal`、`DateTime`、数组、`HashSet<>`、接口、`object` 或未加 `[DataBase]` 的普通 class；确有需求时先扩展并测试生成器，而不是绕过 Parser。
- 嵌套泛型虽然生成器有递归处理能力，仍需通过现有同类数据和实际生成结果验证，避免构造难以维护的多层容器。

### 阶段 6.3：执行 Parser 生成

1. 保存 `Assets/HotUpdate/DataBase/DataModel/<Domain>Data.cs`，确保 Unity Console 没有编译错误。
2. 在 Unity 菜单执行 `PeekabooGame/DBParser生成`。
3. 检查 Console 中 `<TypeName>Parser.AutoGen.cs` 的生成结果和总生成数量。
4. 检查 `Assets/HotUpdate/DataBase/AutoGen/<Domain>DataParser.AutoGen.cs` 存在，并位于 `db.parser` 命名空间。
5. 检查所有 `[DataBase]` 子类型均有对应 Parser；生成失败时修正 DataModel 类型，不手改生成文件。
6. 重新编译，确认 `DataBaseManager` 可以按 `db.parser.<TypeName>Parser` 规则加载 Parser。

生成文件的固定命名关系为：

- Root：`<Domain>Data` -> `<Domain>DataParser.AutoGen.cs` -> `partial class <Domain>DataParser`。
- 子数据：`<BeanName>` -> `<BeanName>Parser.AutoGen.cs` -> `partial class <BeanName>Parser`。
- Root Parser 通过生成的 `Ins` 入口访问，例如 `<Domain>DataParser.Ins`；业务代码不直接实例化 Parser。

### 阶段 6.4：在 ParserExtend 编写数据库内部操作

在 `Assets/HotUpdate/DataBase/ParserExtend/<Domain>DataParser.cs` 中扩展生成类型：

```csharp
using db.cfg;
using db.core;

namespace db.parser
{
    public partial class <Domain>DataParser
    {
        // 在这里封装针对当前 Root 的增删改查和幂等迁移操作。
    }
}
```

ParserExtend 负责数据库内部操作：

- 通过生成属性安全读取 Root 字段。
- 封装 `Set/Add/Remove/Clear/TryGet/Get/Has` 等针对当前 Root 的原子数据操作。
- 创建或更新 `[DataBase]` 子对象，并使用对应子 Parser 修改字段。
- 处理集合为空、记录不存在、重复添加等数据库结构细节。
- 实现只依赖当前 Root 的幂等默认值补齐和版本迁移辅助方法。

Module 仍负责业务规则：

- 配置、功能开放、消耗、条件和权限校验。
- 多 Module 事务编排、奖励发放、业务错误码和事件发送。
- 决定何时调用 ParserExtend，不把“是否允许升级、是否扣费成功”等业务判断下沉到数据库 Parser。

这样可以避免 Module 堆积复杂字典写入和子 Parser 操作，同时防止 ParserExtend 反向依赖 UI、配置玩法或其他业务 Module。

### 阶段 6.5：保存与迁移流程

- 通过生成属性、`MonitorList`、`MonitorDictionary` 或 ParserExtend 方法修改数据，让 Parser 的 `Save()` 链路进入当前项目的帧末保存队列。
- 禁止在 Module 中取得底层 Datasource 后直接改字段；这会绕过生成属性和自动保存监控。
- 需要迁移时，在 Root 增加明确的 `schemaVersion`，并在 ParserExtend 编写 `MigrateFromV<Old>ToV<New>` 等幂等方法。
- 迁移入口在数据库加载完成且业务读取前执行；每一步成功后更新版本，重复执行不得再次发奖励或重复追加集合。
- 旧档中新增集合可能为 `null`，首次访问或迁移时必须补为空集合；新增子对象必须提供明确默认值。
- 迁移失败时使用项目统一日志记录 Root、旧版本、目标版本和异常，不更新版本号，也不继续发送模块初始化完成事件。

**代码规范与命名规则**

- DataModel 文件名和 Root 类名统一为 `<Domain>Data.cs / <Domain>Data`；子数据使用 `<Domain>Info`、`<Domain>Record` 或明确业务名，不能与配置生成类型同名造成歧义。
- DataModel 的 `public` 字段沿用当前项目 `camelCase`；稳定标识以 `Id` 结尾，集合按当前项目使用 `List/Dic` 后缀或明确索引关系，避免 `dataList`、`infoDic` 等缺少领域词的名字。
- AutoGen 属性由生成器把字段首字母转为大写，例如 `roleInfoDic -> RoleInfoDic`；ParserExtend 必须使用生成属性，不复制一套字段访问器。
- ParserExtend 文件和类名固定为 `<Domain>DataParser.cs / partial class <Domain>DataParser`；方法使用 `Set...`、`Add...`、`Remove...`、`Clear...`、`TryGet...`、`Get...`、`Has...` 表达数据库动作。
- 当前项目方法参数沿用 `_camelCase`，例如 `_roleId`、`_level`；新增代码保持同一风格，不在同文件混用多种参数前缀。
- 数据操作方法只描述结构变化，例如 `SetRoleInfo`；包含扣费、条件、奖励或事件的完整业务方法仍命名并放在 Module。
- 存档版本使用明确的 `schemaVersion`，迁移方法命名为 `MigrateFromV<Old>ToV<New>`。序列化字段不得为了代码整洁随意改名。

**完成标准**

- `DataModel/<Domain>Data.cs`、`AutoGen/<Domain>DataParser.AutoGen.cs` 和需要时的 `ParserExtend/<Domain>DataParser.cs` 职责与命名对应。
- Unity 菜单生成无错误，`DataBaseManager` 能加载 Root Parser，修改操作能触发自动保存。
- 保存、重启和旧档迁移后恢复相同业务状态；重复初始化和重复迁移不会重复奖励或破坏已有数据。
- Module 中没有重复展开复杂的字典、列表和子 Parser 写入逻辑，也没有把业务条件和跨模块事务下沉到 ParserExtend。

**常见错误**

- 忘记给 Root 加 `[DatabaseRoot]`、子数据加 `[DataBase]`，导致菜单没有生成对应 Parser。
- DataModel 使用属性、私有字段或不支持的类型，生成器无法识别。
- 手改 `AutoGen/*.AutoGen.cs`，下一次执行菜单后修改丢失。
- 在 Module 里直接操作复杂字典和子 Parser，形成大量重复、漏保存的数据库写入代码。
- 把扣费、条件、奖励和事件放进 ParserExtend，导致数据库层依赖业务层。
- 集合或旧档新增字段为 `null`，首次读取时空引用。
- 用货币为零等合法业务值判断新用户，或迁移方法重复执行后重复发奖励。

## 阶段 7：定义公开查询、命令和结果契约

**输入与项目事实**

- 业务用例、失败原因、项目统一错误码和回调风格。

**工作内容**

- 查询接口只读且无副作用，返回值对象、只读视图或拷贝。
- 命令接口表达完整意图，例如解锁、升级、装备或领奖。
- 定义命令结果、错误原因、输入合法性和事务副作用。
- 为公开接口补详细中文注释，说明配置来源、前置条件、保存和事件。

**代码规范与命名规则**

- 无副作用查询使用 `Get`、`TryGet`、`Has`、`Is`、`Can`、`Calculate`；`Get` 不得暗中创建或保存数据，`TryGet` 必须通过返回值明确成功与否。
- 修改命令使用明确动词，如 `Unlock`、`Upgrade`、`Equip`、`Claim`、`Add`、`Remove`、`Cost`。需要表达可失败事务时，按项目风格使用 `Try<Action>` 或让 `<Action>` 返回 `<Action>Result`。
- 请求和结果类型分别使用 `<Action>Request`、`<Action>Result`；错误枚举使用 `E<Domain>Error` 或项目统一错误码，不以 `bool` 代替所有失败原因。
- 异步方法返回 `Task` 时以 `Async` 结尾；回调参数使用 `onComplete`、`onSuccess`、`onFailed` 等明确名称。
- 方法参数使用领域名而不是类型名缩写；无项目约定时使用 `camelCase`，禁止 `a`、`obj`、`data` 等上下文不足的参数名。

**完成标准**

- UI、function、guide 和其他 Module 不需要接触内部存档即可完成调用。
- 调用方能区分成功、条件不足、配置错误、重复操作和系统异常。

**常见错误**

- 只暴露细粒度字段写接口，让 UI 自己组合业务规则。
- 失败只写日志，不返回可处理结果。

## 阶段 8：创建 Module 并接入生命周期

**输入与项目事实**

- 当前项目的 Module 代码目录为 `Assets/HotUpdate/Modules/`，模块调度器为 `Assets/HotUpdate/Modules/ModuleHandler.cs`。
- Module 基类位于 `Assets/HotUpdate/Module/ModuleBase.cs`，接口位于 `Assets/HotUpdate/Module/IModule.cs`。
- 当前项目真实生命周期顺序为：`Init -> LoadConfigDone -> Login -> LoginDone -> Logout -> Dispose`。业务 Module 通过重写 `OnInit / OnLoadConfigDone / OnLogin / OnLoginDone / OnLogout / OnDispose` 接入，不能自行发明另一套生命周期。
- 数据库映射使用阶段 6 生成的 `<Domain>DataParser`；错误通过 `EErrorCode + ErrorHandler.SendError(...)` 返回；业务成功后通过 `EventConst` 通知 UI 和其他模块。
- 如果目标项目目录或基类不同，先读取其真实 Module 示例并建立等价映射，禁止把本项目路径原样硬套到其他项目。

**工作内容**

### 8.1 创建 `<Domain>Module`

1. 在 `Assets/HotUpdate/Modules/` 下创建 `<Domain>Module.cs`，类名固定为 `<Domain>Module`，继承 `ModuleBase<<Domain>Module>`。
2. 从职责最接近的现有 Module 提炼文件结构、命名和调用方式，不复制与新领域无关的业务代码。
3. 按实际需要重写生命周期方法；空方法不要为了“看起来完整”全部重写。
4. `ModuleBase.Init()` 会先调用 `AddEventListeners()`，再调用 `OnInit()`，因此业务 Module 不得再次手动调用 `AddEventListeners()`。

结构示意只用于说明当前项目入口，实际代码必须从目标项目同类 Module 提炼：

```csharp
public class <Domain>Module : ModuleBase<<Domain>Module>
{
    protected override void AddEventListeners()
    {
        // 注册与模块整个生命周期一致的事件；参数含义必须写中文注释。
    }

    protected override void OnLoadConfigDone()
    {
        base.OnLoadConfigDone();
        // 配置加载完成后建立只读索引和缓存，不读取玩家数据库。
    }

    protected override void OnLogin()
    {
        base.OnLogin();
        // 玩家数据库可用后执行幂等的新用户初始化和旧档补全。
    }

    protected override void OnLoginDone()
    {
        base.OnLoginDone();
        // 所有 Module 的 OnLogin 已完成，可执行依赖其他模块的登录后编排。
    }

    protected override void OnLogout()
    {
        base.OnLogout();
        // 清理当前账号缓存、临时状态和账号级回调，避免串号。
    }

    protected override void OnDispose()
    {
        base.OnDispose();
        // 释放进程级缓存和外部引用；不要在此开始新的业务写入。
    }
}
```

### 8.2 注册到 `ModuleHandler.moduleList`

1. 打开 `Assets/HotUpdate/Modules/ModuleHandler.cs`。
2. 在 `moduleList` 中加入 `<Domain>Module.Instance`。不得在 UI、场景脚本或其他入口里再次 `new` Module。
3. 注册顺序必须满足依赖：被依赖 Module 放前面，消费它的 Module 放后面。例如新模块依赖货币、物品和属性时，应放在这些基础模块之后。
4. 检查 `moduleList` 中没有重复实例；否则所有生命周期、默认初始化和事件监听都会执行两次。
5. 注册后确认 `Run / Login / Logout / Dispose` 会自然遍历到新 Module，不额外手动调用其生命周期。
6. 如果排序后仍出现 A Module 调用 B、B 又反向调用 A，不要继续调整列表掩盖循环依赖；应把公共能力下沉到基础 Module，或改为公开查询、事件通知和独立编排层。
7. 检查新文件是否已经进入项目真实热更新程序集和 `HotUpdate.csproj`。如果项目文件由 Unity 或生成工具维护，应通过项目既有流程刷新，禁止手写一份平行工程配置。
8. 完成 Unity 资源数据库刷新或重新导入后，确认编辑器和打包编译都能发现新 Module，避免只在 IDE 中可见、构建时缺失。

### 8.3 分配生命周期职责

- `AddEventListeners()`：只注册模块长期需要的事件。使用基类 `AddEvent(...)`，同一事件只注册一次；事件回调只接收通知并转入私有业务方法。
- `OnInit()`：初始化不依赖配置、不依赖玩家数据的纯运行时对象。此时不能读取 `ConfigSystem.CurrentData` 的业务表，也不能访问 `<Domain>DataParser` 的玩家数据。
- `OnLoadConfigDone()`：读取配置并建立只读索引、反查字典和静态缓存；对缺失配置使用 `LogUtil.Error` 输出明确的表名和 id。这里不做新用户发奖或数据库写入。
- `OnLogin()`：读取 `<Domain>DataParser.Ins`，执行新用户默认数据创建、空集合补全和旧档迁移。所有初始化必须幂等，重复执行不能重复发奖励、重复解锁或覆盖玩家已有值。
- `OnLoginDone()`：此时所有 Module 的 `OnLogin()` 都已经执行完毕，可调用依赖模块完成跨模块补全、红点刷新或登录后通知。不能把本模块最基本的数据创建拖到这里。
- `OnLogout()`：清理当前账号的临时缓存、选择状态、未完成请求和账号级引用。配置生成的静态索引若与账号无关可以保留，否则必须清空。
- `OnDispose()`：释放模块最终持有的缓存、回调和外部资源。`ModuleBase.Dispose()` 会执行框架事件清理，但模块自行接入的非框架回调仍须成对注销。

### 8.4 封装数据库访问边界

- UI、Manager、引导、战斗和其他 Module 禁止直接访问 `<Domain>DataParser.Ins`、`<Domain>Data` 或数据库 Root。
- 对外读取统一通过 `<Domain>Module`：单值使用 `Get...`，带失败分支使用 `TryGet...`，状态判断使用 `Is... / Has... / Can...`。
- 对外业务写入统一使用 `Send_XXXX(...)`，返回 `bool`。`true` 表示校验和数据库写入全部成功，并且成功事件已经发送；`false` 表示没有完成本次业务写入。
- `Set...` 只作为 Module 私有辅助方法或 `ParserExtend` 内部落库方法，不作为 UI 或其他 Module 的公开写入口。外部需要修改状态时必须调用对应 `Send_XXXX(...)`。
- 查询集合时返回副本、只读视图或专用快照，不能把数据库内部可变 `List / Dictionary` 引用直接交给外部修改。

### 8.5 编写 `Send_XXXX` 业务写入方法

每个会改变玩家数据的公开方法都按以下顺序执行：

1. 校验参数、配置、解锁状态、次数、等级、消耗和前置条件；任何一项失败都不得修改数据库。
2. 为每个可预期失败原因在 `EErrorCode` 中定义 `<Domain>_<Reason>` 错误码，并写中文注释。
3. 校验失败时调用 `ErrorHandler.SendError(EErrorCode.<Domain>_<Reason>)` 并返回 `false`。当前 `ErrorHandler.SendError(int)` 本身返回 `false`，可直接 `return ErrorHandler.SendError(...)`。
4. 涉及多项消耗或多表修改时，先完成全部校验，再统一扣除和写入；禁止边校验边写入导致半成功。
5. 简单字段可由 Module 调用生成的 Parser 属性或方法写入；字典、列表、去重、排序和复合结构操作应调用阶段 6 中 `ParserExtend` 提供的 `Set... / Add... / Remove...` 内部方法。
6. 只有数据库写入和关联事务全部成功后，才调用 `SendEvent(EventConst.<Domain>_<Action>Success, ...)`。
7. 最后返回 `true`。失败路径不能发送成功事件，成功路径不能漏发更新事件。

```csharp
/// <summary>
/// 执行领域业务写入。返回 true 表示数据已成功写入，并已发送刷新事件。
/// </summary>
public bool Send_<Action>(int _id)
{
    if (!Is<Action>Valid(_id))
    {
        return ErrorHandler.SendError(EErrorCode.<Domain>_<Reason>);
    }

    // 复杂集合写入收口在 ParserExtend，Module 只负责业务校验和调用顺序。
    if (!<Domain>DataParser.Ins.Set<Action>(_id))
    {
        return ErrorHandler.SendError(EErrorCode.Exception_Error);
    }

    // 数据成功后再通知 UI 和其他模块，避免监听方读到旧值。
    SendEvent(EventConst.<Domain>_<Action>Success, _id);
    return true;
}
```

上面的 `Set<Action>` 返回值应服从目标项目真实 ParserExtend 设计；如果现有内部写方法为 `void`，不要只为套示例强行改签名，而应在调用前完成可失败校验，并在无异常完成后发送事件和返回 `true`。

### 8.6 定义错误码和更新事件

- `EErrorCode.OK` 固定为 `0`；框架异常等特殊错误可以使用项目已经约定的负数，不占用正常业务编号段。
- 通用模块错误码必须小于 `1000`，使用范围为 `1~999`。货币、物品、通用消耗、通用条件等多个系统都会复用的错误放在这个范围；`1000` 保留不用，作为通用段与业务段的边界。
- 业务模块从 `1001` 开始，按千位为每个 Module 分配互不重叠的独立编号段：第一个业务模块使用 `1001~1999`，下一个模块使用 `2001~2999`，之后依次类推。每个模块的本地编号从 `001` 递增，不使用段首的 `X000`。
- 新建业务 Module 前必须先搜索 `EErrorCode` 已使用的编号段，再选择下一个未占用千位段；禁止不同 Module 共用同一个业务段，也不能只看当前文件末尾数字后随意插入。
- 已经发布或进入存档、日志、埋点和配置的错误码不得改号或复用。删除旧业务时保留其错误码占位，避免历史数据被解释成另一个错误。
- 错误码字段统一命名为 `<Domain>_XXX`：`<Domain>` 与 Module 领域名一致，`XXX` 使用能表达失败原因的英文单词并用下划线分隔，例如 `<Domain>_Not_Unlock`、`<Domain>_Level_Max`、`<Domain>_Param_Error`。禁止使用 `Error1`、`Invalid` 等缺少领域语义的名字。
- 每个错误码后必须写中文注释，说明用户可理解的失败原因；`Send_XXXX` 中使用的每一种可预期失败都应有明确错误码，不能全部退化成 `Exception_Error`。
- 对应错误文本按项目错误配置规则补齐；禁止只定义错误码而没有可展示文本。
- 在 `EventConst` 中定义成功或刷新事件，命名为 `<Domain>_<Action>Success` 或 `<Domain>_Refresh`。事件参数的类型、顺序和含义必须写中文注释。
- 事件表示已经发生的事实，不承担数据库写入职责。监听方只能刷新自身状态或发起下一条明确命令，不能回头直接修改本模块数据库。

### 8.7 提供 UI 和跨 Module API

- UI 读取：调用 `<Domain>Module.Instance.Get... / TryGet... / Is... / Can...`，监听 `EventConst` 后重新查询，不缓存数据库可变引用。
- UI 写入：只调用 `<Domain>Module.Instance.Send_XXXX(...)`，根据返回值决定是否继续交互；错误展示由 `ErrorHandler` 统一负责。
- 其他 Module 读取和写入遵循同一边界，不能因为都在业务层就绕过 `<Domain>Module` 直接操作 `<Domain>DataParser`。
- Module 间需要组合事务时，由数据所有者 Module 提供原子接口，或由上层编排先完整校验再依次调用；不得让调用方知道数据库内部字段布局。
- `function`、`guide` 和战斗只调用公开接口或消费只读快照，不持有养成数据库引用。

**代码规范与命名规则**

- 文件名和类名固定为 `<Domain>Module.cs / <Domain>Module`；不要同时创建同义的 `<Domain>Manager`。
- 生命周期必须使用框架原名和访问级别：`AddEventListeners / OnInit / OnLoadConfigDone / OnLogin / OnLoginDone / OnLogout / OnDispose`。
- 公开写方法固定使用 `Send_` 前缀并返回 `bool`；公开查询使用 `Get / TryGet / Is / Has / Can`；内部数据写辅助方法使用 `Set / Add / Remove / Clear`。
- 当前项目方法参数使用 `_camelCase`；私有字段沿用现有 Module 的 `camelCase`；类型、公开成员和常量使用 `PascalCase`。若目标项目已有更严格约定，服从目标项目。
- 私有辅助方法使用动词开头，例如 `BuildConfigCache / ValidateUpgrade / ClearLoginCache / OnItemRefresh`，不得使用 `DoSomething / HandleData` 等含义模糊的名字。
- 类内顺序按：字段、生命周期、`Send_` 写接口、公开查询、事件回调、私有辅助方法；可用 `#region` 区分，但不要制造多层嵌套区域。
- 关键字段、生命周期职责、`Send_` 事务顺序、错误兜底和事件参数必须写 UTF-8 中文注释；注释说明“为什么和何时”，不机械复述代码。
- 单个方法只负责一个明确业务动作；复杂数据库结构操作下沉 `ParserExtend`，Module 不堆叠大量字典和列表写入细节。

**完成标准**

- `<Domain>Module.Instance` 已按依赖顺序加入 `ModuleHandler.moduleList`，所有生命周期能被实际调用。
- 每个生命周期方法只访问该阶段已就绪的依赖；重复登录、登出和释放不会重复初始化、重复注册或保留旧账号缓存。
- UI 和其他 Module 中不存在对 `<Domain>DataParser.Ins` 或 `<Domain>Data` 的直接访问。
- 所有公开数据写入都经过返回 `bool` 的 `Send_XXXX`；失败调用 `ErrorHandler.SendError`，成功写入后发送对应 `EventConst`。
- 通用错误码位于 `1~999`，业务 Module 各自使用独立的 `1001~1999 / 2001~2999 / ...` 千位段，字段名符合 `<Domain>_XXX`。
- 新增错误码、错误文本和事件参数均有正常中文说明；关键逻辑没有乱码。

**常见错误**

- 忘记把 Module 加入 `moduleList`，导致代码存在但生命周期从未执行。
- 注册顺序早于依赖 Module，导致 `OnLogin` 或 `OnLoginDone` 读取未初始化数据。
- UI 或其他 Module 直接调用 Parser，绕过业务校验、错误码和事件。
- `Send_XXXX` 先写数据再校验消耗，或部分写入失败后没有回滚。
- 校验失败只返回 `false`，没有定义 `EErrorCode` 和调用 `ErrorHandler.SendError`。
- 两个业务 Module 使用同一个千位编号段，或修改、复用已经发布的历史错误码。
- 错误码字段没有 `<Domain>_` 前缀，导致无法从日志快速判断错误归属。
- 写入成功后先发事件再落库，监听方立即查询时读到旧数据。
- 把公开写方法命名为 `Set...`，使调用方误以为可以绕过完整业务事务。
- `OnLogin` 重复执行时重复发新手奖励，或 `OnLogout` 未清理账号缓存造成串号。

## 阶段 9：实现原子业务事务

**输入与项目事实**

- 公开命令、配置、存档模型和公共 Cost、Bonus、Currency、Item、Condition 能力。

**工作内容**

- 严格执行“解析 -> 完整校验 -> 构造变更 -> 原子提交 -> 标脏保存 -> 成功事件”。
- 多资源消耗一次性校验，任一不足时不修改任何数据。
- 奖励先固定结果，再统一发放；一次性操作增加幂等保护。
- 保存或提交失败时按项目能力回滚，禁止发送成功事件。

**代码规范与命名规则**

- 事务入口使用完整业务动词；校验方法使用 `Can<Action>`、`Validate<Action>`，变更构造使用 `Build<Action>Changes`，提交辅助方法使用 `Commit<Action>`，不要都叫 `Handle` 或 `Process`。
- 校验返回项目统一结果或明确错误码；不得用 `null`、`-1` 等隐式约定表示多种失败。
- 使用前置校验和早返回减少嵌套，但提交区域必须集中，不能在多个校验分支散落写操作。
- 变量名区分 `current`、`required`、`remaining`、`before`、`after`，数量变量带 `Count/Amount`，避免复用一个 `value` 表示不同阶段。
- 魔法数、默认等级和倍率必须来自配置、常量或有依据的参数；常量名称必须表达规则含义和单位。

**完成标准**

- 成功请求得到完整结果，失败请求不留下部分修改。
- 重复点击、回调重入和重启恢复不会重复扣除或发放。

**常见错误**

- 在循环里检查一项、扣一项。
- 数据还未提交就先通知 UI 成功。

## 阶段 10：定义事件并完成监听清理

**输入与项目事实**

- 项目业务事件、系统事件和强类型事件的使用边界。

**工作内容**

- 定义已经发生的事实型事件，并注释参数顺序、类型和发送时机。
- 事件携带稳定 ID、旧值、新值、结果和来源，不传可变 Root。
- 数据成功提交后发送；监听在对应生命周期成对注销。

**代码规范与命名规则**

- 事件名表达已经发生的事实。无项目约定时使用 `<Domain>_<Fact>`；强类型事件对象使用 `<Domain><Fact>Event`，例如升级完成而不是“执行升级”。
- 事件处理方法使用 `On<EventName>`；注册和注销方法使用成对的 `Register.../Unregister...` 或 `Add.../Remove...`。
- 事件参数名写清 `id`、`beforeValue`、`afterValue`、`reason` 等语义，并在事件定义处用中文注释固定顺序和类型。
- 避免只有 `Refresh`、`Changed` 而不知道变化对象的宽泛事件；确需聚合刷新时写清触发范围。
- 不在事件名中混入 UI 节点名，业务事件与页面事件分开。

**完成标准**

- UI 和外围系统能通过事件刷新，但核心事务不依赖 UI 监听才能完成。
- 重复进入页面、登录和登出不会重复触发回调。

**常见错误**

- 事件参数靠调用者猜测，发送端与接收端顺序不一致。
- 把事件当作跨模块事务，导致监听失败后数据不完整。

## 阶段 11：接入 UI、function 和 guide

**输入与项目事实**

- UI 基类、面板生命周期、功能入口和引导系统公开接口。

**工作内容**

- 涉及完整养成界面、Prefab 字段契约、AutoGen、Panel/Item、按钮状态或事件刷新时，读取并执行 `$develop-unity-progression-ui`；养成模块只提供业务查询、命令和成功事件。
- UI 打开时查询当前状态，按钮只提交完整业务命令。
- UI 根据命令结果显示失败原因，根据成功事件重新查询刷新。
- function 只负责开放和入口；guide 只负责步骤、遮罩和进度。
- 为任务 UI、红点或外围系统提供只读查询和刷新事件。

**代码规范与命名规则**

- UI 类型沿用项目的 `Panel`、`View`、`Item`、`Widget` 后缀；不要把业务 Module 命名为 Controller，也不要在 UI 类中创建同名业务服务。
- 按钮回调使用 `On<Command>Click` 或项目既有格式，事件回调使用 `On<Fact>`，刷新方法使用 `Refresh<Section>`，避免多个含义不明的 `UpdateUI`。
- UI 展示数据使用 `<Domain>ViewData` 或项目已有 DTO 后缀，不直接暴露持久化 Root。
- `function` 和 `guide` 的接入方法必须体现用途，例如 `Open<Domain>`、`CanEnter<Domain>`、`On<Domain>Completed`，不把步骤编号写进养成公开 API 名称。
- 序列化控件字段使用项目 AutoGen 规则；手写字段不得与生成字段重名。

**完成标准**

- UI、function 和 guide 没有直接写存档，也没有复制业务校验和消耗公式。
- Prefab 和 AutoGen 由 UI Skill 的协作流程接入，手写业务没有落入生成文件。
- 面板关闭后监听正确清理，重复打开不会叠加回调。

**常见错误**

- UI 先改显示值再假设事务一定成功。
- 把页面跳转或引导步骤写进养成 Module。

## 阶段 12：生成并接入战斗快照

**输入与项目事实**

- 上阵角色、装备、等级、品质、永久属性和战斗需要的数据契约。

**工作内容**

- 使用 `$develop-unity-ecs-battle` 对齐战斗读取接口。
- 养成模块根据当前真值和配置生成值拷贝、深拷贝或只读快照。
- 共享属性定义在 `cfg/attribute/`，战斗专属参数留在 `cfg/battle/`。
- 明确战斗期间局外升级只影响下一次快照，局内临时变化不回写基础数据。

**代码规范与命名规则**

- 快照类型使用 `<Domain>BattleSnapshot` 或战斗 Skill 已有命名；创建入口使用 `CreateBattleSnapshot`、`BuildBattleSnapshot`，同一项目只选一种动词。
- 快照字段使用战斗含义明确的名词，ID 以 `Id` 结尾，属性集合使用 `attributes`、`attributeByType` 或项目现有名称。
- 拷贝方法使用 `Clone`、`CopyFrom` 或专门构造函数，并在中文注释中明确深拷贝边界；不要用名为 `ConvertData` 的泛化方法隐藏引用共享。
- 局外永久属性和局内临时属性使用不同类型或字段名，禁止两个字典都叫 `attrDic` 而靠调用方猜来源。
- 快照类型优先不可变或只暴露只读集合，避免公开 `Set` 方法供战斗回写。

**完成标准**

- 战斗能只凭快照创建完整局内对象。
- 修改战斗快照内的集合不会改变玩家存档或养成缓存。

**常见错误**

- 把存档字典引用直接交给战斗组件。
- 战斗运行中重新查询局外等级，造成同一场属性变化。

## 阶段 13：补充注释、日志和项目接入

**输入与项目事实**

- 项目中文注释、日志、错误码、程序集、热更新和 Unity 编辑器规范。

**工作内容**

- 为关键字段、公开方法、事务顺序、配置单位、迁移和异常兜底补详细中文注释。
- 日志包含模块、业务对象、失败阶段和必要上下文，不泄露敏感数据。
- 检查项目文件、程序集定义、Unity `.meta`、Prefab、序列化字段和 AutoGen 工作。
- 只修改需求涉及区域，不顺手清理无关代码或生成文件。

**代码规范与命名规则**

- 公开类型和公开方法按项目规则补 XML 注释；关键私有逻辑用中文注释解释“为什么、顺序、单位、失败影响”，不逐行翻译赋值。
- 日志方法服从目标项目统一入口；消息格式包含领域、动作和关键 ID，例如 `[<Domain>] <Action> failed`，禁止直接使用临时 `Debug.Log` 代替项目日志。
- 异常变量使用 `exception` 或项目既有 `ex`，日志中保留堆栈；不吞掉异常后继续发送成功事件。
- 方法体保持单一职责；复杂事务拆成校验、构造、提交和通知四类私有方法，避免超长入口混合所有流程。
- `#region`、局部函数、扩展方法和 `partial` 只在目标项目已有相同用法且确有必要时使用。

**完成标准**

- 编辑器、热更新编译和目标平台构建都能发现新模块。
- 后续开发者能从注释理解数据来源、规则原因和副作用。

**常见错误**

- 代码在编辑器可运行，但未进入热更新程序集或打包工程。
- 注释机械翻译代码，没有说明为什么和何时清理。

## 阶段 14：执行完整验证

**输入与项目事实**

- 项目真实生成、编译、测试命令和手动入口。

**工作内容**

- 执行配置生成、静态搜索、C# 编译和已有自动测试。
- 验证新用户初始化、成功事务、失败事务、重复请求、最大等级和非法配置。
- 保存后重启验证数据恢复；使用旧档验证迁移和重复迁移。
- 验证事件只在成功后发送、UI 不直接写数据、监听没有泄漏。
- 涉及战斗时验证快照稳定、深拷贝和局内变化不回写。

**代码规范与命名规则**

- 测试类使用 `<TypeUnderTest>Tests` 或目标项目既有后缀；测试方法无约定时使用 `<Method>_<Scenario>_<Expected>`，名称必须能直接说明场景和结果。
- 测试数据构造器使用 `<Domain>TestBuilder`、`CreateValid...` 等明确名称，不在测试里堆叠无法解释的数字。
- 每个失败分支单独测试，避免一个测试同时验证资源不足、满级和配置缺失而难以定位失败。
- 测试专用入口、调试开关和假数据必须放在测试或开发工具边界，不能污染正式公开 API。
- 静态搜索同时检查不规范占位名、遗留旧类型名、未使用事件和手改生成文件。

**完成标准**

- `references/验证规范.md` 的相关项目全部有结果。
- 未执行的验证有明确原因、残余风险和后续操作人。

**常见错误**

- 只验证成功路径，不验证资源不足和保存失败。
- 只编译代码，未实际验证存档重启和旧档迁移。

## 推荐代码落地顺序

1. 配置源和配置生成。
2. 持久化 Root、强类型子数据和迁移。
3. 查询、命令、结果和错误契约。
4. Module 与生命周期实现。
5. Module 注册和依赖顺序。
6. 原子事务和业务规则。
7. 事件定义、发送和解绑。
8. UI、function、guide 和红点接口。
9. 战斗快照及战斗接入（如涉及）。
10. 项目文件、Unity 编辑器工作、测试和交付文档。

这个顺序允许代码在每个阶段保持职责清晰，也能在依赖尚未准备好时尽早发现问题。若目标项目有更严格的本地顺序，以项目文档为准，并在方案中说明差异。

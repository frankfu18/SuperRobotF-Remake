# 经济事务与通用模块

## 通用模块职责

- **Currency**：维护货币余额、上下限、增减和余额变更事件。
- **Item**：维护堆叠物品数量、获得、消耗和物品变更事件。
- **Cost**：解析多种消耗定义，检查是否满足，并构造扣除计划。
- **Bonus**：解析奖励内容，先确定随机结果，再构造发放计划。
- **Condition**：只判断条件并返回原因，不直接扣除或发奖。
- **Attribute**：提供跨养成和战斗共享的属性类型、单位和基础运算契约。

这些模块只提供稳定能力，不写死角色升级、装备强化、商店购买或活动领奖等具体业务。

## 标准事务顺序

任何购买、升级、解锁或领奖都按以下顺序执行：

1. 解析配置和请求参数。
2. 校验功能状态、配置存在、次数、等级、背包容量和所有条件。
3. 一次性检查全部货币和物品是否足够。
4. 构造消耗、奖励和目标业务数据的变更计划。
5. 原子提交全部变更；任一步失败则全部回滚。
6. 标脏并保存。
7. 发送业务成功事件和基础资源变化事件。
8. UI 根据事件重新查询，不使用提交前缓存自行推算。

严禁在循环中“检查一项、扣一项”。多项消耗只要有一项不足，就不能修改任何余额。

## 数量与来源

- 数量必须大于零；减法前检查下溢，加法前检查上限和溢出。
- 经济写操作携带稳定来源原因，例如升级、奖励、补偿或调试，便于日志和数据分析。
- 错误结果使用项目统一错误码或结果对象，不能只靠日志告诉 UI 失败。
- 基础模块事件应包含资源类型、ID、旧值、新值和来源；具体业务成功事件包含业务对象 ID 和结果等级等信息。

## 奖励与幂等

- 奖励计算与发放分离，随机奖励先把结果固定成不可变列表。
- 一次性奖励需要领取状态或幂等键；重复请求返回已领取，不重复发放。
- 网络重试、按钮连点、回调重入和重启恢复都必须验证。
- 奖励展示使用实际发放结果，而不是重新随机或重新解析配置。

## 条件系统

条件判断应是无副作用查询。组合条件明确“全部满足”或“任一满足”，失败时可返回首个失败原因或完整失败列表。具体玩法条件通过扩展类型或适配器接入，公共条件层不能反向依赖角色、竞技场或活动模块。

## 扩展系统

商店、任务、签到、邮件、活动和通行证使用同一事务入口：它们负责次数、状态和业务配置，实际资源扣除与发放委托给 Cost、Bonus、Currency 和 Item。扩展系统不能复制一套余额修改逻辑。
